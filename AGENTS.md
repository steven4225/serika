# Runloom Development Constraints

## Project workflow

- Discuss and explicitly confirm a module's behavior before implementing it.
- Implement only the currently confirmed scope. Do not preemptively add database schemas, adapters, public APIs, or abstractions for later milestones.
- Before changing an already confirmed invariant or state-machine rule, explain the impact and obtain explicit confirmation.
- Keep changes focused on the current module. Do not perform unrelated refactors or dependency upgrades.
- Do not commit or push unless the user explicitly asks for a version-control checkpoint.

## Terminology and architecture

- The project name is Runloom.
- Core domain language uses `Thread`; do not introduce `Session` as an alias.
- Preserve this dependency direction:

  ```text
  Application / Harness
          -> Durable Runtime
          -> Orchestrator
          -> ModelInvoker / ToolExecutor ports
          <- infrastructure adapters
  ```

- The Orchestrator is a pure state machine. It must not access PostgreSQL, call models or tools, read the system clock, generate IDs, or perform external effects.
- PostgreSQL is the durable source of truth. Do not add Redis, Kafka, or another source of execution truth in the MVP.

## Durable execution invariants

- The identity hierarchy is `Thread -> Run -> Turn -> Action -> Attempt`; an Approval binds to a Tool Action.
- A Thread has at most one active Run in the MVP.
- Each external effect is represented by one Action; each real invocation is represented by a new persisted Attempt.
- External model and tool calls run outside database transactions. Persist intent before the call and persist its resolution in a new short transaction afterward.
- AI SDK and Tool adapters do not retry tools or hide retries by default. The interactive TUI may explicitly opt into bounded model-request retries for a still-empty step; Durable Runtime remains the owner of external-effect retry policy and every real invocation must remain auditable as an Attempt.
- A tool without an explicit replay-safety classification is treated as non-idempotent and defaults to one attempt.
- Never automatically retry a non-idempotent tool when dispatch or outcome is unknown; transition to reconciliation instead.
- Approval is persisted before any Tool Attempt is created. Approval authorizes execution but does not execute the tool inside the approval transaction.
- Terminal Run states never transition back to a non-terminal state.
- Do not hide an unknown external side effect as an ordinary failure, cancellation, or timeout.

## MVP boundaries

- Do not add multi-worker execution, parallel tools, queued Runs, Steering, Follow-up, multi-agent orchestration, RAG, automatic memory writes, or inferred global memory unless a later design discussion explicitly promotes it into scope. Explicit user-managed workspace memory, read-only candidate proposals, and its versioned lifecycle are part of the current TUI scope; memory text never grants execution permission; committed transcript text and compaction summaries are not current preferences, only the injected memory version is.
- PostgreSQL may be selected as the persistence target while tests continue to use deterministic in-memory fakes around explicit ports.

## Local behavior milestone

- M-Local is a local behavior harness built from `DefaultAgentRuntime`, `AgentLoop`, and transcript-only JSONL snapshots. It does not replace Durable Runtime or provide durable external-effect guarantees.
- `AgentLoop` is the only owner of the model -> tool -> model behavior loop. A future Durable Run Driver may persist and invoke already-decided Actions and Attempts, but must not introduce a second behavior loop.
- M-Local JSONL stores only completed conversation transcripts. Embedded AssistantController also writes a separate, bounded local execution-receipt file in the transcript directory for Run/tool inspection after restart. These receipts are not Durable Runtime state: an unfinished tool is `unknown`, must be reconciled by a person, and is never replayed automatically. TUI/print CLI do not enable this receipt path.
- Embedded WorkTask state is an explicit, workspace-local task contract, not an implicit wrapper around every chat Run. A primary Run must be linked to its WorkTask at the execution-record create barrier; Run completion only pauses the task or sends uncertain receipts to review. Task completion requires a submitted delivery and evidence-backed required criteria: exact successful Shell receipts and current artifacts with task-owned write receipts may be checked automatically, while human criteria require explicit user acceptance. Unknown effects are never replayed, and product WorkTask completion is distinct from an external Eval pass.

## Thin TUI boundary

- M-TUI-thin's Agent execution path only calls `run`, `handle.events`, `handle.result`, and `handle.cancel`; idle input may dispatch an explicitly registered module command without adding a command bus, session object, or second loop.
- TUI may read committed transcript messages from the Store for display, but must never put that history into `RunRequest.messages` or maintain a second messages cache.
- Its visible state is `idle | running(handle)`. While running, ordinary input is rejected as busy rather than queued; when a tool confirmation is pending, input belongs to that confirmation. Only `handle.result` returns the UI to idle.
- TUI confirmation is a single in-memory `beforeToolExecute` hook: `y` allows the current call, `n` returns `TOOL_DENIED`, and any other line keeps waiting. Abort rejects the hook with the abort reason and never becomes a denial. There is no approval queue, and a `y` is never remembered. If `web_search` is denied with `n` in the current Run, later `web_fetch` calls in that Run return `TOOL_DENIED` without a prompt and without a network request; the latch clears when the Run ends.
- An explicit `/authorize` may grant the next Run automatic `{ allow: true }` for only the listed file tools and workspace-relative path prefixes; all other tools and paths keep the original `y/n` confirmation, with no approval queue.
- Persistent file authorization may come only from explicit `fileAuthorizations` in the TUI config; the config must resolve outside the workspace, rules load at startup, and editing or removing them takes effect after restart. Memory text and transcripts never grant permission.
- Memory candidate proposals are ordinary assistant replies built from committed user messages; they are not persisted candidates and cannot write memory without a later explicit user selection and the existing tool confirmation. Manual consolidation material contains only ordinary user text. Automatic consolidation derives its cursor from the latest committed auto-consolidation turn, bootstraps at most eight ordinary turns when no cursor exists, skips turns that used `memory_*`, and may include bounded assistant/tool evidence as context only; `mode: "incremental"` is accepted only from `memory-consolidator`. A failed consolidation, including input that exceeds the consolidation budget, creates no cursor and is retried from the last committed boundary. A conversation source is recorded only after the application verifies that its message id belongs to a unique committed user text message in the active Thread and that its quote is an exact substring of that message. A mismatch is rejected. Assistant text, tool results, webpages, and auto-consolidation turns are not user-fact sources. Direct same-Run remember requests keep manual source because that user message is not committed yet. Asking why a memory was saved uses `memory_get`; its quote is the excerpt verified at save time and is not a claim that `/history` can still open the original message.
- TUI `--check` is a read-only static preflight: it may parse configuration and inspect required local paths and credential presence, but must not create a Thread, transcript, store, temporary directory, Run, network request, or worker. Its success does not prove authentication, worker liveness, or task quality. `/modules` may re-read Memory for the current injectable count using the production selector; corrupt Memory is an error rather than an empty set, and no Memory text or history is printed there.
- Docker Shell sandbox is opt-in through `modules.shell.sandbox`; it mounts only declared workspace paths, uses no network, and never falls back to host execution when Docker is unavailable. `/authorize-shell` is next-Run only; it never creates persistent Shell permission.
- Web fetching is opt-in through `modules.web.enabled`; `web_fetch` is public HTTP(S) GET-only, validates every redirect target and DNS result, carries no cookies or application secrets, and returns bounded text with provenance/truncation. A public hostname whose DNS answer is Clash/Surge fake-ip (`198.18.0.0/15`) is not treated as a private fetch target; IP literals in that range and RFC1918/loopback/link-local/metadata targets stay blocked. `/authorize-web` is exact-origin, next-Run-only permission for `web_fetch`; web content is data, never execution instructions. `web_search` is separately opt-in through `modules.web.search.enabled`, uses the keyless Exa hosted MCP search tool without a paid-API fallback, remains read-only and per-call confirmed, and only discovers sources; factual claims require `web_fetch`. Research may select at most two sources per baseline task, must distinguish discovered/verified/partial/failed sources, must cite `finalUrl`, and may claim a saved report only after `write_file` succeeds. Browser automation, login, uploads, and worker web tools are out of scope.
- M9 `modules.web.feed.enabled` is an optional, per-call-confirmed public RSS/Atom reader under the enabled web module. It shares web fetch target/DNS/redirect/timeout and 512 KiB limits but reads raw feed XML without HTML extraction or 64 KiB text clipping; incomplete bodies and non-UTF-8 XML are rejected. Items retain document order; titles/summaries are untrusted discovery data, article claims require a separate successful `web_fetch`. Feed links outside public HTTP(S) become null. `/authorize-web` still authorizes only `web_fetch`, while a denied `web_search` blocks both `web_fetch` and `feed_read` for that Run. No subscription, polling, background input, automatic memory or task write, or QQ/WeChat/email connector is implied.
- When idle, a line trimmed to start with `/` is dispatched to the registered command map; commands do not create Runs or transcript messages. Confirmation input has priority over commands, and running or run-starting input is rejected as busy. A command that returns a thenable must finish before the next input line is accepted.
- When older complete turns are omitted from the model prompt, TUI injects a process-local work summary in `prepareModelContext` only. The summary is not written to the transcript or a separate persistence file; reopening the same transcript directory and thread deterministically rebuilds it from that thread's committed messages, without mixing in other threads. This is conversation-context reconstruction, not Durable recovery: uncommitted actions from failed or cancelled Runs and all tool authorizations remain unrestored. Goal text is the original request, not current world state; completed items are short `ok:true` tool receipts. Idle `/history` reads the current thread's committed transcript messages from the Store.
- The optional workspace checkpoint is separate from Memory and transcript, one versioned current snapshot per workspace. Its TUI tools are explicitly user-requested and use normal `y/n`; `checkpoint_prepare` only returns current checkpoint plus injectable Memory and does not call a model or collect conversation turns. Only current is injected as a bounded reference in both normal and compaction context; it is not live disk evidence and grants no tool permission. Active Memory wins conflicts. Corrupt or oversized checkpoint data is never partially used or overwritten; checkpoint tools do not count as `memory_*` for automatic-consolidation gating.
- With checkpoint enabled, idle `/resume` performs a bounded local Git read and reconciles it with the optional program-owned pin saved by `checkpoint_save`. The observation is process-only and for the next primary Run; it creates no Run or JSONL, does not restore approval, and does not imply file, test, or PR verification. Git failure omits the pin on save or yields insufficient evidence on resume; it does not authorize other tools or create a second agent loop.
- M7 Home is a read-only TUI display after committed history and before the first prompt; `/home` rereads the same sources and awaits complete output. It reads checkpoint and local task stores directly, independently reports failures, never creates a Run or writes/acks state, never auto-inspects Git, and does not claim desktop notification delivery. Checkpoint source Thread and temporary transcript directory/Thread identity must be explicit; command hints follow enabled modules only.
- M8 one-time task rescheduling updates the existing task ID and `runAt` under the same task-store lock as worker claim; it never cancels and recreates a task. Only a scheduled non-recurring instance may be rescheduled, even when its old due time has passed; the new time must be in the future. The `task_reschedule` tool uses ordinary Run `y/n` with a best-effort current-time preview, while the idle `/task reschedule` command writes directly like other task commands. A claim between preview and execution returns `TASK_NOT_RESCHEDULABLE`; a successful tool reschedule remains a completed-action receipt if the Run later fails or stops. Neither path implies that a worker is running or a desktop notification was delivered.
- M10 `--workspace-context` explicitly lets the task worker read a bounded workspace snapshot once after each claim, independently of TUI module switches, and applies to every task that process claims. Missing Memory or checkpoint is a valid empty source; corrupt, oversized, symlinked, or unreadable sources fail the task before `runtime.run()` with `runId: null`. Inject the captured snapshot via `RunRequest.context` and `prepareModelContext` without re-reading it on later model steps or persisting a separate context record. Only active, unexpired workspace Memory may enter; the current checkpoint is a saved reference, and Memory wins conflicts. Attention inbox input uses `list({ inbox: true, status: "attention", limit })` at the existing list maximum, drops this recurring series, then keeps at most five existing previews and recomputes `truncated`, without promoting this series' past failures to fresh priorities. This switch registers no new worker tools; `--todoist` remains the sole optional read tool. Brief formatting belongs to the scheduled task prompt, not to every worker reply. Existing claim, finish, missed-occurrence, inbox, ack, and notification semantics remain authoritative.
- Context compaction is opt-in through the TUI config's `contextCompaction.enabled`. When enabled, the budget path replaces the R4 eight-turn trimming path and counts instructions, tool definitions, enabled memory, dynamic context, and messages with the versioned `char-half/v1` estimate. It may summarize earlier complete tool interactions, but never splits a tool call from its result or infers permission from a summary. A completed tool result that does not fit beside the current user message is summarized together with that message; a user message that alone exceeds the budget is not replaced by a summary. `thread.context.compacted` records share the JSONL file with v1 committed transcripts; Core treats their payload as opaque, and invalid compaction records do not replace a valid transcript. `/compact` is an idle TUI operation with `idle | running | compacting` state, does not create a Run or consume authorization, and Ctrl+C returns it to idle. Compaction is context reconstruction, not Durable recovery; only a summary matching the latest committed transcript prefix is restored.
- R5's TUI model retry is bounded to the explicit interactive adapter option: at most three model requests for a still-empty step, with 250ms then 1s delays; it never retries tools, worker/print runs, authentication failures, partial output, or a tool-call attempt. A non-idempotent tool whose execution outcome is unknown is reported as `TOOL_OUTCOME_UNKNOWN`, stops the current Run, and requires user verification before any new request; explicit `ok:false` and other structured failures remain ordinary tool failures.
- Development tasks use the existing file and Shell tools in the primary TUI AgentLoop: inspect relevant code, reproduce a reported failure when practical, make a scoped minimal edit, run the requested check directly so its tool `exitCode` is not masked, and report observed results and gaps. User-stated scope does not grant tool permission or sandbox host Shell; do not auto-commit, push, or merge. A05 requires independent diff and command-result review, not the assistant's success claim alone. The primary TUI Run stays at 8 model steps unless config `run.maxSteps` sets an integer from 1 to 32. That setting does not change total timeout, step timeout, shell timeout, confirmation pause, the consolidation agent, or worker limits, and it does not retry automatically.
- Desktop long-task display uses bounded TUI config `run.totalTimeoutMs` (default 120 seconds, maximum 30 minutes) and `modules.shell.timeoutMs` (default 30 seconds, maximum 10 minutes) without changing step count, confirmation pauses, or worker budgets. Shell stdout/stderr progress is process-local display data tagged with tool call identity and sequence; it is not a Core event, transcript record, model context, or success receipt. Final `shell_exec` output and actual exit/timeout/cancellation fields remain authoritative. No tool replay or crash recovery is implied.
- Ctrl+C cancels a running handle and waits for its result; Ctrl+C while idle exits. If startup is still awaiting `runtime.run()`, or stdin closes, record the stop request and cancel as soon as the handle arrives.

## PostgreSQL persistence

- The PostgreSQL adapter lives in `packages/postgres`; Core must not import `pg`, Kysely, migration types, SQLSTATE types, or database row types.
- Use `pg` for pooling, Kysely for typed queries and short transaction callbacks, and `node-pg-migrate` for immutable forward migration history. Never run migrations automatically during application startup.
- Persist current relational state rather than event-sourcing `DurableEvent`. IDs are Runtime-generated non-empty text values; PostgreSQL does not generate domain identities.
- Use strong columns for identity, status, time, versions, scheduling, constraints and frequently queried discriminators. Use versioned JSONB payloads only for JSON content, model/tool data, resolutions, errors and evidence.
- Only Runloom `JsonValue` crosses a JSONB boundary. Do not persist SDK objects, `undefined`, `Date`, `BigInt`, class instances or non-finite numbers.
- Stable request and tool-input hashes use the versioned `jcs-sha256:v1` protocol over RFC 8785 canonical JSON; never hash `jsonb::text`.
- An external Effect and its `Attempt(not_dispatched)` are committed atomically. The Effect remains in `effect_outbox` until a separate transaction records the dispatch boundary and removes the row.
- `EffectDispatcher` is a non-reentrant, single-worker batch service. Outbox scans are hints; the locked Run transaction must revalidate the candidate and commit `dispatched` before invoking an external port.
- ModelInvoker and ToolExecutor are SDK-neutral Core ports. They receive immutable invocation data plus one Runtime-owned `AbortSignal`; they never retry, persist state, create IDs, or decide orchestration policy.
- A Tool invocation is pinned by `toolsetVersion`, `toolName` and `toolCallId`. Do not resolve an active Run against an unversioned current Tool implementation.
- `not_applied` requires proof that no external side effect occurred. Timeouts, connection loss and unclassified Adapter errors are `outcome_unknown`; an unknown non-idempotent Tool always requires reconciliation.
- Persist a Stop Request before aborting an active in-process Attempt. Active AbortControllers are process-local acceleration and never replace durable Stop state.
- Duplicate Outbox writes are idempotent only when their complete Effect payloads match. A conflicting payload is an invariant failure, not `ON CONFLICT DO NOTHING` success.
- PostgreSQL integration tests use the pinned `postgres:18.4-alpine` Testcontainer and the same Repository Contract as the in-memory reference adapter.

## Testing and quality

- Use TypeScript strict mode and keep domain types free of AI SDK, database, and transport-specific objects.
- Every state transition must have deterministic tests for its normal path and relevant idempotency, cancellation/deadline, concurrency, and crash-recovery edge cases.
- Prefer pure transition tests before repository or adapter integration tests.
- Run `pnpm typecheck` and `pnpm test` before requesting a code checkpoint.

## Documentation and repository hygiene

- Keep confirmed developer constraints in this `AGENTS.md`.
- Runtime specifications, discussion notes, scratch files, and personal knowledge-base material are local working documents unless the user explicitly approves versioning a specific file.
- Do not stage local specifications or notes merely because they are under the repository directory.
- Never commit credentials, `.env` files, generated output, dependency directories, editor state, or Obsidian metadata.
