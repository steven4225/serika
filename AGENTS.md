# Runloom Development Constraints

## Project workflow

- Discuss and explicitly confirm a module's behavior before implementing it.
- Implement only the currently confirmed scope. Do not preemptively add database schemas, adapters, public APIs, or abstractions for later milestones.
- Before changing an already confirmed invariant or state-machine rule, explain the impact and obtain explicit confirmation.
- Keep changes focused on the current module. Do not perform unrelated refactors or dependency upgrades.
- Do not commit or push unless the user explicitly asks for a version-control checkpoint.

## Maintenance-phase task admission

- Apply this gate once the project is explicitly in its maintenance phase. Adding this rule does not declare that the current project is already in maintenance.
- Do not use "完善", "优化", "增强健壮性", "重构", or "补充能力" as standalone development goals. Technical changes may be implementation means, not the user outcome.
- Before admitting any maintenance task into development, state all three:
  - **Before:** What can the user not do today, or which complete action currently fails?
  - **After:** What complete action can the user perform after this version?
  - **Demo:** How can the user personally verify the result within five minutes? Specify the entry point, necessary preconditions, steps, and observable pass/fail result.
- If no concrete five-minute Demo can be given, the task must not enter development. Clarify the user outcome first.
- Code changes, passing unit tests, test counts, and an assistant's success claim do not substitute for the user-observable Demo.

## Terminology and architecture

- The project name is Runloom.
- Core domain language uses `Thread`; do not introduce `Session` as an alias.
- Preserve this dependency direction:

  ```text
  Application / Harness
          -> Durable Runtime
          -> Orchestrator
          -> ModelInvoker / ToolExecutor ports
          <- infrastructure adapters
  ```

- The Orchestrator is a pure state machine. It must not access PostgreSQL, call models or tools, read the system clock, generate IDs, or perform external effects.
- PostgreSQL is the durable source of truth. Do not add Redis, Kafka, or another source of execution truth in the MVP.

## Durable execution invariants

- The identity hierarchy is `Thread -> Run -> Turn -> Action -> Attempt`; an Approval binds to a Tool Action.
- A Thread has at most one active Run in the MVP.
- Each external effect is represented by one Action; each real invocation is represented by a new persisted Attempt.
- External model and tool calls run outside database transactions. Persist intent before the call and persist its resolution in a new short transaction afterward.
- AI SDK and Tool adapters do not retry tools or hide retries by default. The interactive TUI may explicitly opt into bounded model-request retries for a still-empty step; Durable Runtime remains the owner of external-effect retry policy and every real invocation must remain auditable as an Attempt.
- A tool without an explicit replay-safety classification is treated as non-idempotent and defaults to one attempt.
- Never automatically retry a non-idempotent tool when dispatch or outcome is unknown; transition to reconciliation instead.
- Approval is persisted before any Tool Attempt is created. Approval authorizes execution but does not execute the tool inside the approval transaction.
- Terminal Run states never transition back to a non-terminal state.
- Do not hide an unknown external side effect as an ordinary failure, cancellation, or timeout.

## MVP boundaries

- Do not add multi-worker execution, parallel tools, queued Runs, Follow-up, multi-agent orchestration, RAG, automatic memory writes, or inferred global memory unless a later design discussion explicitly promotes it into scope. Controller foreground-primary Steer is explicitly promoted: opt-in, bounded same-Run user corrections at safe boundaries, superseding unstarted tool calls and their approvals without cancelling executing tools, extending budget, granting permission or replaying accepted requests after restart. TUI and workers do not enable it. Explicit user-managed workspace memory, read-only candidate proposals, and its versioned lifecycle are part of the current TUI scope; memory text never grants execution permission; committed transcript text and compaction summaries are not current preferences, only the injected memory version is.
- PostgreSQL may be selected as the persistence target while tests continue to use deterministic in-memory fakes around explicit ports.

## Local behavior milestone

- Confirmed personal-assistant scope supersedes the earlier pending-only/foreground-only memory boundaries: explicit external `modules.memory.writePolicy: "automatic"` plus enabled auto-consolidation permits host-approved classifications of new, source-validated incremental proposals to become formal memory atomically with candidate receipts and cursor. Missing classification, ambiguous proposals, selected history and existing pending candidates remain review-only. The model judges semantics; exact source checks do not prove truth. Program message exclusion is the hard opt-out; recognized credential/consent phrases are conservative probes, not universal privacy classification. Temporal revisions, CAS, scope/pin restrictions, uncertain-commit handling and explicit undo remain.
- Automatic consolidation is one preemptible application lifecycle, not a second loop or resident reflection service. In automatic mode, ordinary primary chat has no direct Memory tools: current references are host-injected, while explicit review/history/pin/restore/delete remain desktop Controller operations. Legacy review mode retains approved tools. Ordinary chat reserves foreground admission, cancels background work and awaits actual settlement before starting another Run; manual maintenance/WorkTask operations still require idle. Startup processes only the current Thread's committed backlog under its existing leases. Cancellation does not advance the cursor and routine foreground yielding is not a consolidation failure.
- Confirmed scheduled arrangements extend the existing TaskStore/worker: typed reminder, read-only Todoist planning and exact-bound RSS only, with per-arrangement source declarations and purpose-based notifications. Typed reminders and empty RSS checks may use audited deterministic outcomes with no model Run; new declarations do not inherit global workspace Memory/checkpoint access. Generic task tools cannot forge RSS bindings. One creation approval may explicitly authorize saving the arrangement and the embedding host enabling its configured workspace service; these are not an atomic cross-system transaction, so service failure must return the saved arrangement plus an unavailable-service result. Never enable a service on app startup or silently replace an incompatible registered service. Fixed-offset typed recurrence coalesces missed slots to the latest due occurrence. OS notification submission remains distinct from receipt, ack and native click routing.
- Explicit trusted `--notification-helper` outside the workspace may submit macOS notifications with a bounded task-result URL. Only task ID and workspace digest enter that URL; it grants no execution, acknowledgement or workspace-switch authority. Desktop rereads the current workspace record and supports cold/warm navigation; invalid or foreign links fail before data reads. Basic osascript notifications retain no click-routing claim. Helper installation and system notification consent are separate from code/test acceptance. launchd stop must confirm job absence before removing its definition; opt-in native tests touch only an isolated workspace and service label.

- M-Local is a local behavior harness built from `DefaultAgentRuntime`, `AgentLoop`, and transcript-only JSONL. Committed v1 snapshots remain readable; v3 writes contain hashed chunked message deltas and periodic full checkpoints under the same append lock. Incomplete transactions are not committed messages; physical cleanup never deletes logical messages or grants execution authority. It does not replace Durable Runtime or provide durable external-effect guarantees.
- `AgentLoop` is the only owner of the model -> tool -> model behavior loop. A future Durable Run Driver may persist and invoke already-decided Actions and Attempts, but must not introduce a second behavior loop.
- M-Local JSONL stores only completed conversation transcripts. Embedded AssistantController also writes a separate, bounded local execution-receipt file in the transcript directory for Run/tool inspection after restart. These receipts are not Durable Runtime state: an unfinished tool is `unknown`, must be reconciled by a person, and is never replayed automatically. TUI/print CLI do not enable this receipt path.
- Embedded WorkTask state is an explicit, workspace-local task contract, not an implicit wrapper around every chat Run. A primary Run must be linked to its WorkTask at the execution-record create barrier; Run completion only pauses the task or sends uncertain receipts to review. On controller startup, acquire the workspace/Thread WorkTask lease and transcript/Thread execution lease before marking unfinished execution records interrupted and reconciling their running WorkTasks; missing, foreign, or `unknown` effects require review, while fully accounted records may pause, and nothing is replayed automatically. `reconcileWorkTask()` records a bounded human report rather than program evidence: `continue` only returns the task to `paused` for a later explicit `runWorkTask()`, and `cancel` never proves that an earlier side effect did not occur. Task completion still requires a submitted delivery and evidence-backed required criteria: exact successful Shell receipts and current artifacts with task-owned write receipts may be checked automatically, while human criteria require explicit user acceptance. Product WorkTask completion is distinct from an external Eval pass.

## Thin TUI boundary

- M-TUI-thin's Agent execution path only calls `run`, `handle.events`, `handle.result`, and `handle.cancel`; idle input may dispatch an explicitly registered module command without adding a command bus, session object, or second loop.
- TUI may read committed transcript messages from the Store for display, but must never put that history into `RunRequest.messages` or maintain a second messages cache.
- Its visible state is `idle | running(handle)`. While running, ordinary input is rejected as busy rather than queued; when a tool confirmation is pending, input belongs to that confirmation. Only `handle.result` returns the UI to idle.
- TUI confirmation is a single in-memory `beforeToolExecute` hook: `y` allows the current call, `n` returns `TOOL_DENIED`, and any other line keeps waiting. Abort rejects the hook with the abort reason and never becomes a denial. There is no approval queue, and a `y` is never remembered. If `web_search` is denied with `n` in the current Run, later `web_fetch` calls in that Run return `TOOL_DENIED` without a prompt and without a network request; the latch clears when the Run ends.
- An explicit `/authorize` may grant the next Run automatic `{ allow: true }` for only the listed file tools and workspace-relative path prefixes; all other tools and paths keep the original `y/n` confirmation, with no approval queue.
- Persistent file authorization may come only from explicit `fileAuthorizations` in the TUI config; the config must resolve outside the workspace, rules load at startup, and editing or removing them takes effect after restart. Memory text and transcripts never grant permission.
- Native Memory A persists validated pending candidates, not active facts. The shared application-layer consolidation service prepares committed ordinary user material, stages exactly one batch, and only after a completed Run atomically writes candidates and automatic cursor to `memory.json` v4 under the existing flock. Failed/cancelled/invalid batches do not advance the cursor. Bootstrap takes at most eight eligible turns; subsequent batches take the oldest eligible backlog without skipping it. The cursor binds ordered user ids and exact text; old transcript prepare markers are not completion evidence. Assistant replies, tools, webpages, summaries, and synthetic consolidation messages are never user-fact sources. Quotes must exactly match a unique committed user message in the prepared window; mismatches cannot become manual sources. Direct same-Run `memory_add` instead binds the current ordinary user message ID and exact quote in the host, before transcript commit, with the existing per-call approval. The model cannot choose the source ID; absent or synthetic current sources fail rather than becoming manual sources. This does not change consolidation's committed-source rules or automatic mode's toolset.
- Memory correctness batch 5 makes the built-in consolidator host-prepared, tool-free, one model step with no model-request retry: its bounded JSON extraction must contain an ordered `extracted | no_memory | deferred` outcome for each source. The host validates and stages before the existing completed-Run atomic commit. The cursor stops before the first deferred source; missing legacy coverage is all deferred, never an inferred empty/no-memory result. A latest bounded incremental coverage receipt per Thread shares the MemoryStore commit and prefix hash; selected history cannot replace it. Partial-source proposals may commit without advancing that source, and later preparation retains the deferred source across restart/new messages. Four optional fact attributes (response language, review format, coffee, residence) have explicit scenario/value identities; only same-slot same-value observations reuse text/time and bounded sources. Differing adds require review, explicit changes retain bitemporal segments, legacy facts are not heuristically assigned identities, and these model classifications are not proof of semantic truth or universal recall. No LLM deletion/merging to free capacity is allowed.
- Candidates belong to their origin Thread and never enter primary/worker context. Explicit Controller review uses current candidate revision and the existing idle mutex without a Run; model acceptance uses `memory_apply_candidate` with normal y/n. Denial leaves pending; rejection changes only the candidate. Acceptance atomically writes active Memory plus the candidate receipt, rechecking target revision/expiry; exact replay returns the old receipt without another write. Active edits invalidate related update candidates; permanent deletion purges related candidate content. Only the consolidator's exact prepare/stage tools may bypass confirmation. File v1-v3 reads normalize without migration; successful actual mutations write v4. Storage is bounded to 512 entries/16 MiB, pending to 64 and terminal candidates to 256. Storage capacity is separate from the 8 KiB final reference budget. `pinned` may be changed only by explicit user operations, never by automatic candidates. `memory_get` quotes show verified saved excerpts, not a promise that `/history` still has the original message.
- Oversized whole-source fallback is a host-only `not_saved / too_large` coverage disposition, never model-reported `no_memory`: its source ID and exact prepared prefix share the atomic receipt/cursor commit, original transcript remains intact, and the Controller asks the user to split it. A valid short exact quote from a long source remains eligible. Incremental deferred or rejected host extraction persists at most three source attempts in that same prefix-bound receipt, with receipt CAS even when the cursor stays unchanged. The third becomes explicit `not_saved / retry_exhausted`, not a saved or empty result; retained facts/reviews survive, the original remains available for explicit history processing, and later messages unblock. Cancellation, changed evidence and pre-rename persistence failure never consume an attempt or cursor. Post-rename uncertainty is never progress evidence or retried automatically: read current state before deciding what applied. Model stages cannot forge attempts or terminal dispositions, and there is no immediate model-request retry loop.
- Memory temporal storage keeps v4 assertions as the sole fact source; old flat CRUD returns derived current projections, never raw timelines in context. Explicit storage operations distinguish real `change`, `correct`, `retract`, and new-revision `restore` under CAS. Valid time and system time are separate half-open intervals; unknown legacy dates/coverage are not invented, and source validation remains the trusted caller's responsibility. System clocks are captured once under flock; backwards writes fail. A logical entry retains at most 64 assertions and 64 administrative revision references, rejecting capacity rather than silently pruning. Restore defaults to contents effective now and requires explicit choices for disabled/expired records; no tool authority or deleted records revive. Writes sync the temporary file, rename atomically and sync the directory; post-rename acknowledgement failures are `MEMORY_COMMIT_UNCERTAIN`, not proof of zero writes. Non-idempotent model writes stop as unknown, while exact candidate receipt replay remains write-free. `deleteMemory` adds revision-CAS permanent deletion; the compatibility ID-only delete remains explicit. Retrieval enhancements, new temporal model tools, background reflection and desktop temporal editing are not part of this storage slice.
- Native Memory B defaults to pure lexical retrieval, no persistent index, embedding or vector service. Explicit `modules.memory.queryRewrite.enabled` extends ordinary primary chat with at most one cached, five-second, no-retry auxiliary model query per current user message; it sees only the bounded question and may return at most three short retrieval phrases, never facts or writes. Failure degrades to original lexical retrieval, caller cancellation aborts. WorkTasks, worker, checkpoint, manual compact and consolidation do not rewrite. Original lexical matches precede rewritten matches under the same scope/expiry/enabled/budget filters; there is no guaranteed semantic recall or relevance. Normalize only retrieval copies (NFKC/lowercase, English words and Chinese adjacent bigrams); exact source checks remain unchanged. Query is at most 4 KiB on Unicode boundaries; at most two pins/4 KiB precede matched entries, final reference at most 12 entries/8 KiB including JSON packaging. No zero-match filler, no half-entry clipping, and no strong-paraphrase recall claim. Current user text supplies the primary query before compaction; each preparation reads/selects once and shares its complete reference prefix between the compactor budget and final injection. Manual compact queries the latest committed ordinary user text; the next Run retrieves anew. Empty selected reference is not an empty-store/deletion claim, and old replies/summary IDs are not current injected evidence. References include id/revision/text, never history/candidates/sourceQuote. Worker uses task.prompt and one fixed workspace-only snapshot; checkpoint_prepare uses empty-query pins plus selection metadata; consolidation uses the same lexical ordering but may include visible disabled/expired current versions for conflicts. /modules distinguishes storage, eligible and pinned-preview counts, not next-Run hits. User requests and system rules remain authoritative; Memory does not grant tool permissions.
- Embedded formal-memory management lists only workspace/current-Thread entries, including disabled/expired current versions, independently of candidate history. Explicit idle edits permit text, pin/unpin and disable only under current revision CAS; they create no Run and may not forge sources or scope. Text edits become manual sources, with old source in existing history. Successful context preparation publishes a process-local, message/Run-bound reference snapshot (IDs, revisions, text and selection reasons), not model self-report; failed preparation clears it and restart does not restore it. This snapshot is preparation evidence, not current Memory truth, confirmed provider delivery or proof that the answer obeyed a preference.
- Confirmed semantic upgrade extends Native Memory B only by explicit external `modules.memory.semantic.enabled`: a compatible `/embeddings` client with batches of at most ten, no chat credentials, redirect or retries, and a five-second total preparation deadline. Observed `qwen3.7-text-embedding-flash` batch responses have ambiguous all-zero indexes; that explicit cloud model uses one string per request with at most ten concurrent requests, each vector bound to its request, never response-order inference or automatic batch fallback/retry. Explicit `provider: "dashscope"` authorizes sending bounded queries and already-eligible current formal text to official HTTPS DashScope compatible endpoints (legacy Beijing/Singapore or real Beijing/Singapore/Hong Kong workspace domains), using only host `DASHSCOPE_API_KEY`. Credentials never enter config/cache/report and upstream error bodies/transport exception text are not retained. Missing keys degrade at preparation, not app startup. Missing provider remains loopback-only local for legacy privacy compatibility; no silent cloud upgrade, installation or download. A rebuildable `.runloom/memory-semantic-index.json` cache contains vectors keyed by endpoint/model, ID, revision and text hash, never a second fact source. Cold preparations index at most twenty missing eligible facts; warming is partial coverage, not full readiness. Lexical/vector reciprocal-rank fusion retains scope/current-time/revision filters, pins and the shared twelve-fact/eight-KiB packaging budget; unavailable services degrade visibly to lexical retrieval. Only ordinary primary chat opts in, not worker, checkpoint, manual compact or consolidation. Same-message unchanged query/fact preparations reuse process-only query results; fresh formal projections are rechecked after inference. Real embedding quality and deployment remain separate acceptance.
- Explicit `modules.memory.contextView.enabled` derives up to three supported general current preference projections and three current-Thread unfinished WorkTask summaries within two KiB of that same eight-KiB reference budget. It creates no profile store, new plan, authority, tool replay or model loop; scenario-limited, disabled, expired, retracted and foreign-Thread facts remain excluded. New desktop configurations enable this view; existing configurations are not silently upgraded.
- Kind is only a relevance tie-break in lexical/vector retrieval: current preference/fact before event/note, never ahead of a stronger match, pins or eligibility. No heat, quotas or type thresholds. Derived profile also rejects a body scene when old identity metadata says general. Everyday affirmative current transitions (从现在起／以后／今后／我现在／请把我的…改成 or 改为) still require model-proposed full-source changeIntent and host known-slot/scene/scope/CAS checks; ordinary conflict and ambiguous future/third-party language remain review-only. Real embedding acceptance is a separate opt-in isolated MR suite, not mock pass rates or chat-E2E proof.
- Incremental automatic preference changes may carry source-bound `changeIntent: {type: "replace_from_now", sourceQuote}` without model `effectiveAt`. Only a complete single prepared affirmative self-transition in a known same slot/scene/scope is host-resolved under the commit flock clock; ambiguous/conditional/quoted/ordinary conflicts remain review-only. CAS, old valid-time segments, source evidence, pins and undo remain. The sole paired automatic mutation exception is an identical old-value source attachment followed by its validated from-now change on the same original CAS target: older coverage-order sources stay on the old assertion, new sources on the new assertion, and both transitions are previewed under one lock. Other duplicate-target automatic mutations still fail.
- Temporal Memory B extends pending proposals with up to four exact committed user quotes, approved kind/recallTerms/validTime and distinct real change/correct/retract/disable semantics; old single-source add/update candidates keep their original fingerprints. A real change requires explicit effectiveAt and preserves prior applicability; correction does not invent a real-world transition. Acceptance rechecks target CAS under the same store lock and never changes scope or pins. Related historical assertions, including visible disabled/expired facts, are bounded consolidation-only conflict material, not current primary/worker truth. Whole invalid batches leave candidates and cursor unchanged. The sole content-validation exception is an add whose body or optional fact fields fail: revalidate unchanged provenance and authority, then retain the exact source as review, or defer that source if it cannot fit without clipping; independent valid facts may commit. Source/Thread/scope/unknown-field/eligibility/target-CAS failures still reject the whole batch. Explicit deferred coverage is never promoted by a retained partial fact or review. Controller `run(text, { memoryConsolidation: "exclude" })` persists an exclusion marker, skips that automatic followup and excludes the message from later explicit/automatic consolidation; natural-language opt-out remains model guidance, not this program guarantee. Auto-consolidation and query rewrite remain explicitly configured. Recall ranks original body matches before approved recallTerms, then optional query rewrite; terms are at most three/96 UTF-8 bytes each and never injected as facts. Current references/snapshots include selected assertion identity, applicability/knowledge time and source identifiers, not quotes, terms or raw timelines; events/notes retain their existing date-not-expiry rule. Explicit confirmed `memory_revise` and read-only `memory_query` use the same temporal store; these tools are primary-only, never worker/consolidator tools. Desktop temporal review and real Electron acceptance are a separate slice.
- TUI `--check` is a read-only static preflight: it may parse configuration and inspect required local paths and credential presence, but must not create a Thread, transcript, store, temporary directory, Run, network request, or worker. Its success does not prove authentication, worker liveness, or task quality. `/modules` may re-read Memory for the current injectable count using the production selector; corrupt Memory is an error rather than an empty set, and no Memory text or history is printed there.
- Temporal Memory C exposes scoped, bounded Controller history/query/maintenance reads and explicit idle actions for correction, real change, retraction, metadata, restoration and permanent deletion. Desktop previews use the same store transitions as writes, never write/create a Run/call a model, and are invalidated on refresh; confirmation rechecks revision under flock and captures the actual system time. Renderer inputs cannot forge sources, scope or system timestamps. Restoration creates a new revision with explicit disabled/expired choices, not old authority; deletion is irreversible through this UI. Maintenance is read-only and consolidation finalization failure is not a successful empty proposal batch. Real model, native Electron interaction and full-process restart remain distinct acceptance evidence.
- Explicit desktop consolidation shares the existing idle mutex and consolidator. Selected history binds 1–8 current-Thread eligible committed user IDs in the Controller, never model arguments; missing/excluded messages and an over-budget selected set fail without reducing selection or advancing the automatic cursor. Incremental retry uses the existing failure-safe commit. Consolidator model steps allow 30 seconds within the existing 120-second total; timeout/finalization failures remain failures, not empty proposals. Maintenance attempt/skip diagnostics are process-local, separate from persisted candidate/cursor facts. Exact same pending changes may share one current-Thread review with the original provenance; no semantic deduplication guarantee or automatic formal write is implied.
- Docker Shell sandbox is opt-in through `modules.shell.sandbox`; it mounts only declared workspace paths, uses no network, and never falls back to host execution when Docker is unavailable. `/authorize-shell` is next-Run only; it never creates persistent Shell permission.
- Web fetching is opt-in through `modules.web.enabled`; `web_fetch` is public HTTP(S) GET-only, validates every redirect target and DNS result, carries no cookies or application secrets, and returns bounded text with provenance/truncation. A public hostname whose DNS answer is Clash/Surge fake-ip (`198.18.0.0/15`) is not treated as a private fetch target; IP literals in that range and RFC1918/loopback/link-local/metadata targets stay blocked. `/authorize-web` is exact-origin, next-Run-only permission for `web_fetch`; web content is data, never execution instructions. `web_search` is separately opt-in through `modules.web.search.enabled`, uses the keyless Exa hosted MCP search tool without a paid-API fallback, remains read-only and per-call confirmed, and only discovers sources; factual claims require `web_fetch`. Research may select at most two sources per baseline task, must distinguish discovered/verified/partial/failed sources, must cite `finalUrl`, and may claim a saved report only after `write_file` succeeds. Browser automation, login, uploads, and worker web tools are out of scope.
- M9 `modules.web.feed.enabled` is an optional, per-call-confirmed public RSS/Atom reader under the enabled web module. It shares web fetch target/DNS/redirect/timeout and 512 KiB limits but reads raw feed XML without HTML extraction or 64 KiB text clipping; incomplete bodies and non-UTF-8 XML are rejected. Items retain document order; titles/summaries are untrusted discovery data, article claims require a separate successful `web_fetch`. Feed links outside public HTTP(S) become null. `/authorize-web` still authorizes only `web_fetch`, while a denied `web_search` blocks both `web_fetch` and `feed_read` for that Run. No subscription, polling, background input, automatic memory or task write, or QQ/WeChat/email connector is implied.
- When idle, a line trimmed to start with `/` is dispatched to the registered command map; commands do not create Runs or transcript messages. Confirmation input has priority over commands, and running or run-starting input is rejected as busy. A command that returns a thenable must finish before the next input line is accepted.
- When older complete turns are omitted from the model prompt, TUI injects a process-local work summary in `prepareModelContext` only. The summary is not written to the transcript or a separate persistence file; reopening the same transcript directory and thread deterministically rebuilds it from that thread's committed messages, without mixing in other threads. This is conversation-context reconstruction, not Durable recovery: uncommitted actions from failed or cancelled Runs and all tool authorizations remain unrestored. Goal text is the original request, not current world state; completed items are short `ok:true` tool receipts. Idle `/history` reads the current thread's committed transcript messages from the Store.
- The optional workspace checkpoint is separate from Memory and transcript, one versioned current snapshot per workspace. Its TUI tools are explicitly user-requested and use normal `y/n`; `checkpoint_prepare` only returns current checkpoint plus injectable Memory and does not call a model or collect conversation turns. Only current is injected as a bounded reference in both normal and compaction context; it is not live disk evidence and grants no tool permission. Active Memory wins conflicts. Corrupt or oversized checkpoint data is never partially used or overwritten; checkpoint tools do not count as `memory_*` for automatic-consolidation gating.
- With checkpoint enabled, idle `/resume` performs a bounded local Git read and reconciles it with the optional program-owned pin saved by `checkpoint_save`. The observation is process-only and for the next primary Run; it creates no Run or JSONL, does not restore approval, and does not imply file, test, or PR verification. Git failure omits the pin on save or yields insufficient evidence on resume; it does not authorize other tools or create a second agent loop.
- M7 Home is a read-only TUI display after committed history and before the first prompt; `/home` rereads the same sources and awaits complete output. It reads checkpoint and local task stores directly, independently reports failures, never creates a Run or writes/acks state, never auto-inspects Git, and does not claim desktop notification delivery. Checkpoint source Thread and temporary transcript directory/Thread identity must be explicit; command hints follow enabled modules only.
- M8 one-time task rescheduling updates the existing task ID and `runAt` under the same task-store lock as worker claim; it never cancels and recreates a task. Only a scheduled non-recurring instance may be rescheduled, even when its old due time has passed; the new time must be in the future. The `task_reschedule` tool uses ordinary Run `y/n` with a best-effort current-time preview, while the idle `/task reschedule` command writes directly like other task commands. A claim between preview and execution returns `TASK_NOT_RESCHEDULABLE`; a successful tool reschedule remains a completed-action receipt if the Run later fails or stops. Neither path implies that a worker is running or a desktop notification was delivered.
- M10 `--workspace-context` explicitly lets the task worker read a bounded workspace snapshot once after each claim, independently of TUI module switches, and applies to every task that process claims. Missing Memory or checkpoint is a valid empty source; corrupt, oversized, symlinked, or unreadable sources fail the task before `runtime.run()` with `runId: null`. Inject the captured snapshot via `RunRequest.context` and `prepareModelContext` without re-reading it on later model steps or persisting a separate context record. Only active, unexpired workspace Memory may enter; the current checkpoint is a saved reference, and Memory wins conflicts. Attention inbox input uses `list({ inbox: true, status: "attention", limit })` at the existing list maximum, drops this recurring series, then keeps at most five existing previews and recomputes `truncated`, without promoting this series' past failures to fresh priorities. This switch registers no new worker tools; `--todoist` remains the sole optional read tool. Brief formatting belongs to the scheduled task prompt, not to every worker reply. Existing claim, finish, missed-occurrence, inbox, ack, and notification semantics remain authoritative.
- Background delivery uses the existing single worker lock and v4 TaskStore attempts/outcome/notification records, not a second loop or Durable Runtime. Restart installs only matching persisted outcomes; unfinished executions become interrupted without model/tool replay. Explicit `--safe-retry` permits at most three read-only responder attempts for classified transient model errors. Task terminal state and notification intent are atomic; notification failure retries notification only. `submitted` means OS submission, never user receipt or ack; popups omit prompt/result/Memory. User-level launchd enable/disable is explicit, credentials stay in an external env file, and heartbeat is display evidence rather than ownership authority. Closing a window is supported only with the independent service enabled; sleep/offline punctuality and exactly-once notification are not promised.
- RSS subscriptions explicitly extend M9's on-demand boundary: workspace `.runloom/rss.json` v1 binds one existing recurring series; only that exact series and reserved prompt together with worker `--rss` permit program-owned public feed GETs. No new worker tools or scheduler, task schema stays v4. At most eight sources, twenty observed entries per source, five delivered; first successful delivery establishes the observed-window baseline, not an entire-feed cursor. Stable ID, then public URL, then title/date hash dedupes within a source. A persisted pending batch freezes safe-retry input; only a completed task's durable result advances keys. Failed/interrupted execution releases the batch without swallowing entries; restart settles matching terminal task evidence and never reruns interrupted tasks. Bounded history fails at capacity rather than silently evicting keys. Feed data is untrusted, never automatic Memory, instructions, or verified article facts. Canonical source/error/item lists are program-owned; model notes are separately labeled feed-only. Subscription mutations use revision CAS and explicit user actions, not model tools. Changing subscriptions cannot revoke an already-dispatched GET or already stored result. Cross-file schedule creation can leave a harmless unbound reserved-prompt series on write failure; it has no network authority. OS delivery/launchd evidence boundaries remain unchanged.
- Context compaction is opt-in through the TUI config's `contextCompaction.enabled`. When enabled, the budget path replaces the R4 eight-turn trimming path and counts instructions, tool definitions, enabled memory, dynamic context, and messages with the versioned `char-half/v1` estimate. It may summarize earlier complete tool interactions, but never splits a tool call from its result or infers permission from a summary. A completed tool result that does not fit beside the current user message is summarized together with that message; a user message that alone exceeds the budget is not replaced by a summary. `thread.context.compacted` records share the JSONL file with v1 committed transcripts; Core treats their payload as opaque, and invalid compaction records do not replace a valid transcript. `/compact` is an idle TUI operation with `idle | running | compacting` state, does not create a Run or consume authorization, and Ctrl+C returns it to idle. Compaction is context reconstruction, not Durable recovery; only a summary matching the latest committed transcript prefix is restored.
- R5's TUI model retry is bounded to the explicit interactive adapter option: at most three model requests for a still-empty step, with 250ms then 1s delays; it never retries tools, worker/print runs, authentication failures, partial output, or a tool-call attempt. A non-idempotent tool whose execution outcome is unknown is reported as `TOOL_OUTCOME_UNKNOWN`, stops the current Run, and requires user verification before any new request; explicit `ok:false` and other structured failures remain ordinary tool failures.
- Development tasks use the existing file and Shell tools in the primary TUI AgentLoop: inspect relevant code, reproduce a reported failure when practical, make a scoped minimal edit, run the requested check directly so its tool `exitCode` is not masked, and report observed results and gaps. User-stated scope does not grant tool permission or sandbox host Shell; do not auto-commit, push, or merge. A05 requires independent diff and command-result review, not the assistant's success claim alone. The primary TUI Run stays at 8 model steps unless config `run.maxSteps` sets an integer from 1 to 32. That setting does not change total timeout, step timeout, shell timeout, confirmation pause, the consolidation agent, or worker limits, and it does not retry automatically.
- Desktop long-task display uses bounded TUI config `run.totalTimeoutMs` (default 120 seconds, maximum 30 minutes) and `modules.shell.timeoutMs` (default 30 seconds, maximum 10 minutes) without changing step count, confirmation pauses, or worker budgets. Shell stdout/stderr progress is process-local display data tagged with tool call identity and sequence; it is not a Core event, transcript record, model context, or success receipt. Final `shell_exec` output and actual exit/timeout/cancellation fields remain authoritative. No tool replay or crash recovery is implied.
- Embedded context diagnostics are strictly read-only: reuse transcript-prefix compaction validation, return bounded metadata/metrics rather than summary content, and never prepare context, call a model, create a Run, or write records. Historical valid compaction and process-local last preparation are separate; restart clears the latter, and preparation failure cannot be reported as the previous successful installation. Missing provider usage is not zero. Electron lock holders must run as Node helpers, not a second desktop instance.
- Embedded model usage observes the SDK provider boundary without owning execution/retry policy: chat, consolidation, query rewrite, compaction and explicit Skills share bounded optional metadata in the existing execution journal. Retries are separate call attempts; local rewrite/summary reuse is not a call. Missing cache/token fields and interrupted/cancelled usage remain unknown, never zero; explicit provider/model pricing is snapshotted for estimates only, never invoices. No prompt/raw response/credential retention, worker accounting, historical backfill or tool replay is implied.
- Ctrl+C cancels a running handle and waits for its result; Ctrl+C while idle exits. If startup is still awaiting `runtime.run()`, or stdin closes, record the stop request and cancel as soon as the handle arrives.

## PostgreSQL persistence

- The PostgreSQL adapter lives in `packages/postgres`; Core must not import `pg`, Kysely, migration types, SQLSTATE types, or database row types.
- Use `pg` for pooling, Kysely for typed queries and short transaction callbacks, and `node-pg-migrate` for immutable forward migration history. Never run migrations automatically during application startup.
- Persist current relational state rather than event-sourcing `DurableEvent`. IDs are Runtime-generated non-empty text values; PostgreSQL does not generate domain identities.
- Use strong columns for identity, status, time, versions, scheduling, constraints and frequently queried discriminators. Use versioned JSONB payloads only for JSON content, model/tool data, resolutions, errors and evidence.
- Only Runloom `JsonValue` crosses a JSONB boundary. Do not persist SDK objects, `undefined`, `Date`, `BigInt`, class instances or non-finite numbers.
- Stable request and tool-input hashes use the versioned `jcs-sha256:v1` protocol over RFC 8785 canonical JSON; never hash `jsonb::text`.
- An external Effect and its `Attempt(not_dispatched)` are committed atomically. The Effect remains in `effect_outbox` until a separate transaction records the dispatch boundary and removes the row.
- `EffectDispatcher` is a non-reentrant, single-worker batch service. Outbox scans are hints; the locked Run transaction must revalidate the candidate and commit `dispatched` before invoking an external port.
- ModelInvoker and ToolExecutor are SDK-neutral Core ports. They receive immutable invocation data plus one Runtime-owned `AbortSignal`; they never retry, persist state, create IDs, or decide orchestration policy.
- A Tool invocation is pinned by `toolsetVersion`, `toolName` and `toolCallId`. Do not resolve an active Run against an unversioned current Tool implementation.
- `not_applied` requires proof that no external side effect occurred. Timeouts, connection loss and unclassified Adapter errors are `outcome_unknown`; an unknown non-idempotent Tool always requires reconciliation.
- Persist a Stop Request before aborting an active in-process Attempt. Active AbortControllers are process-local acceleration and never replace durable Stop state.
- Duplicate Outbox writes are idempotent only when their complete Effect payloads match. A conflicting payload is an invariant failure, not `ON CONFLICT DO NOTHING` success.
- PostgreSQL integration tests use the pinned `postgres:18.4-alpine` Testcontainer and the same Repository Contract as the in-memory reference adapter.

## Testing and quality

- Hosted direct `memory_add` saves a non-empty verbatim excerpt from the host-bound current ordinary user message. Optional `sourceQuote` must contain that excerpt and exactly match current user text; omitting it is not permission to import an earlier fact or paraphrase. Approval does not replace source validation. Automatic consolidation may still extract facts under its existing committed-source rules; standalone legacy Memory tools and update/revise contracts are unchanged.

- Follow-up recall extends the query-only rewrite input with at most two prior ordinary user messages from the current Thread, each clipped to 1 KiB on Unicode boundaries. Excluded task messages, synthetic consolidation, assistant text, tools and summaries are not topic hints. The rewriter may use hints only to resolve explicit references, not to invent facts or expand a self-contained new topic; uncertainty should produce no expansion. The first preparation remains cached per current message and query even if later compaction changes history. This is retrieval guidance, not a semantic-relevance guarantee or a new memory source.

- Test freshness includes later dispatched Shell and computer actions as well as file write/edit calls, including failed calls that started. Denied/not-started calls do not invalidate tests. Arbitrary Shell commands are never inferred to be read-only. Multiple required tests with the same exact cwd may use a deterministic, fail-fast `/bin/sh -c` batch within the existing 1 KiB command evidence bound; the exact batch/cwd and successful receipt are rechecked by both finish verification and Store acceptance. Each original command runs in a separate shell; all must succeed in that invocation. This grants no automatic approval and does not attest to test semantics or arbitrary external/background changes. Differing cwd or oversized batches require an explicit revised test contract, not endless correction. Continuation may project the latest owned Run's persisted completion reason; it never overrides task acceptance or restores execution permission.

- Checked embedded WorkTasks extend the original pause-only finish rule: at the existing AgentLoop text-only finish point, a host-owned hook checks required automatic criteria against the latest owned primary Run and current artifacts. Missing correctable evidence may produce at most two corrective prompts within that same Run and its original step/time limits; there is no outer loop, new Run, permission restoration or unknown-effect replay. Exact successful tests must follow the latest file operation. A passing finish check attempts the existing delivery submission after terminal receipt persistence and re-verifies evidence; human criteria remain explicit and the WorkTask acceptance state is authoritative. Ordinary chat is unchanged. Explicit `runWorkTask({ completionCheck: false })` retains partial/manual iteration and is not a checked-completion evaluation. Completion reasons/receipt metadata are not human quality or Eval success; cancelled/unknown effects preserve their original states.

- Research delivery guidance also applies to directly supplied URLs with search disabled: attribute each key conclusion to actual fetched text/finalUrl and its version scope, distinguish missing documentation from runtime proof, and check agreement/difference sections for contradictions. When file tools are enabled, ask the primary model to read back a successfully saved report before delivery; denied/failed/truncated readback is an explicit verification gap, not permission to repeat a write. This is task guidance, not a deterministic factual validator, extra model loop, automatic human acceptance, or a new Core completion rule.

- WorkTask rework is explicit: `requestWorkTaskChanges()` only returns `awaiting_acceptance` to `paused` under revision CAS, retains the last delivery as reference and clears every acceptance result/reference/note. It never starts a Run or replays tools. Acceptance is legal only while awaiting a newly submitted delivery; later automatic evidence must belong to the latest owned primary Run. Terminal tasks cannot reopen and unknown effects still require reconciliation. No multi-version delivery history is implied.

- WorkTask continuation is a bounded projection of the existing task and its latest owned primary receipt, never a new persistent plan or replay log. Explicit next Runs receive historical delivery/unresolved items and at most eight receipt identities, within the existing 24 KiB contract limit; they must read current artifacts before editing and read back changes. This is task guidance, not an additional tool gate or factual validator. Missing/foreign latest receipts never fall back to older Runs. Context preparation identity is process-only, bound to the actual user message/task/Run; manual compaction and restart clear its association. Historical valid compaction alone never proves this task used a summary, provider delivery, or task quality.

- File write/edit success returns SHA-256 of the exact UTF-8 bytes written, not a later disk snapshot. Embedded execution receipts capture bounded `fileInput` intent from the full requested event and `fileWrite` result only after dispatch and a matching successful tool output; a new write's returned hash must match its requested content hash. These optional fields extend the existing v1 journal without backfilling old records, enlarging 2 KiB display previews or changing WorkTask evidence schema. Artifact acceptance rechecks the latest owned primary Run/call, safe current file, byte count and hash; later failed/unknown writes cannot be replaced by earlier successes. Legacy complete previews retain their prior verification path, while legacy truncated receipts stay unverifiable. Malformed compact metadata fails closed; Shell continues to require its exact complete command/cwd receipts. Human quality acceptance may be recorded by an operator only under explicit user authorization, including a scoped delegation that must be identified in the note; this does not create model-owned automatic acceptance or default authority for later tasks.

- Local Computer Use is opt-in through an external trusted config with exact bundle IDs and an absolute Cua Driver executable outside the workspace. Only the primary app registers observe/action tools; no worker/consolidator/print tools, driver installation, daemon autostart, OS permission grants, global input, foreground escalation or pixel API. AX-addressed background operations still depend on the driver's transport, are not an OS sandbox, and require per-call approval. Fresh bounded observations bind bundle/PID/window/token for at most 60 seconds and are consumed before an action; revalidate ownership before dispatch and observe afterward. Transport errors, malformed receipts, unknown/indeterminate/partial outcomes after dispatch escape as unknown non-idempotent outcomes, never retried. A returned dispatched-but-unverifiable receipt allows a fresh read, not repeat action or business-success claims. UI data grants no authority, and an AX/driver receipt is not business-success evidence. Static preflight must not execute the driver.

- `tool.call.failed` with `TOOL_OUTCOME_UNKNOWN` is a failed invocation with an unknown effect, not a proven failed effect. Persist it as an `unknown` execution receipt and settle owned WorkTasks to `needs_review`. Controller activity keeps its compatible completed/failed enum and exposes `outcomeUnknown:true`; cancelled started tools may only be visible as unknown in finalized Run receipts. Native acceptance is explicitly opt-in and narrowly authorizes only an isolated TextEdit fixture; controlled driver faults and programmatic approvals do not prove Electron clicks or actual daemon disconnect handling.

- Use TypeScript strict mode and keep domain types free of AI SDK, database, and transport-specific objects.
- Every state transition must have deterministic tests for its normal path and relevant idempotency, cancellation/deadline, concurrency, and crash-recovery edge cases.
- Prefer pure transition tests before repository or adapter integration tests.
- Run `pnpm typecheck` and `pnpm test` before requesting a code checkpoint.
