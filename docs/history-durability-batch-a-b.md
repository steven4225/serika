# 第一批 A＋B：长历史与关键回执

范围以 `optimization-route-impl-brief.md` 为准。保留当前工作树已有的 v1/v3 兼容与增量写入，不更换记忆框架、不接向量库、不改 Telegram、备份或界面布局。本次不自动提交或迁移全部日用历史。

## Before

- 旧全量快照会积累；总文件超过 16 MiB 曾导致桌面拒读。已有流式读取仍会在每次列表刷新时重新解析旧快照。
- 物理整理与追加已有同路径锁，但锁没有跨越整个 Run 生命周期。
- 回执已有临时文件 sync、rename、目录 sync；可选追踪写入失败却可能被吞掉，且明确写入失败后可能继续尝试派发。

## After

- v1 旧快照仍可读。v3 保存只写改变的后缀，分块与提交记录的校验不变；未提交的块和 EOF 尾巴不是有效消息。
- core 使用进程内增量解码投影：未变化不重读，追加时从上次完整行边界继续；替换、截短、同大小修改使缓存失效。桌面另保留最多 200 个小型列表／搜索投影，避免会话数超过完整历史缓存容量时反复解析。
- 缓存依据本项目的 append/原子替换协议，不支持绕过协议原地篡改旧前缀后再增长文件；离线校验及物理 compact 仍执行完整解析。缓存不是另一份事实源，重启可丢弃，不落盘。
- POSIX 宿主提供的同一追加租约在 Core 创建 Run 前取得，直到终态才释放。Run 内部摘要追加和最终保存复用租约；同实例 active Run 拒绝物理 compact，其他进程先等待该租约。等待租约不占用进程内写入队列，以免挡住原 Run 的保存与退出。
- `compactThread()` 仅去掉重复快照，保留全部当前消息 ID、正文、元数据与不透明伴随记录；没有宿主跨进程锁时禁止替换。默认到 8 MiB 且能明显减少体积才整理，正常运行前自动检查，不增加 UI 管理入口。单条旧记录／一次增量事务仍限 128 MiB；累计有效消息超过单次 checkpoint 上限时跳过物理替换，保留原链继续增量保存，不借整理删除消息。
- transcript、回执、WorkTask 和后台任务的实际写入失败会挡住该实例后续执行写入。rename 后确认失败、transcript 追加后 sync／close 失败仍单独标为提交不确定；只读查看保留，需重开核对，不能重放未知工具。可选追踪也不能吞掉权威回执的损坏或读取失败。正常取消和业务校验失败不等于磁盘故障。
- macOS/Linux 执行 file sync＋目录 sync；Windows 不声称具备 POSIX 目录同步／flock 保证。fsync 调用测试不等于做过断电测试，也不使本地回执成为完整 Durable Runtime。

## 五分钟可重复的存储 Demo

从仓库根目录运行：

```sh
pnpm build:runtime
node --test examples/cli/dist/transcript-maintenance.test.js examples/cli/dist/transcript-storage.test.js
node --test --test-name-pattern='receipt.*sync failure' examples/cli/dist/app.test.js
```

第一条验收建立约 36.9 MB 的旧重复快照，然后使用真实文件存储与 compact 整理至约 216 KB，重开原 Thread，在真实 Runtime／AgentLoop 中继续一次文件读取。输出明确记录 `model: scripted` 和 `electron: not_run`，没有付费模型调用。

可观察通过条件：

1. 原消息逐项相等；正式记忆文件及游标字节不变，已整理来源没有重新进入 backlog。
2. 原合法摘要仍通过前缀哈希校验；缺 `summary.version: 2` 的新记录仍无效。改变来源后，游标和摘要均不能伪装有效。
3. 重开时模型请求数为零，旧写文件没有执行；新读取先等待新确认，只批准一次；继续后仅新增一条待沉淀用户来源。
4. 一个真实子进程尝试 compact 时，被活着 Run 的租约挡住；原 Run 可以保存和结束，随后子进程整理，不丢消息或摘要。
5. 注入回执文件／目录 sync 故障后，真实 Runtime 不发模型请求，磁盘恢复后同一实例也不能启动下一次派发。

## 日用桌面的五分钟操作 Demo（与上面的存储验收分开）

前提：日用 Serika 加载本次构建，空闲且草稿已保存；选用已经显式登记、累计超过 16 MiB 的旧 Thread。不要为了演示混入不明 workspace 的历史，不回放旧任务。若没有这类日用 Thread，存储 fixture 的通过不能写成桌面操作通过。

1. 在现有历史入口搜索该 Thread 的一句旧话，确认标题、命中片段与正文可见。
2. 打开原 Thread，明确发送一条新请求；确认整理不阻塞使用，旧工具没有重放。
3. 完整退出、重开，核对仍是同一个 Thread 和原来的历史。
4. 请求一次文件读取；无当前显式授权时必须出现新的确认，旧批准不能代替它。
5. 若该 Thread 原来有合法摘要和记忆游标，核对上下文诊断与整理状态；不能以历史有效摘要冒充本轮已经使用。

当前新增自动验收覆盖存储与真实执行循环，**不代表这条 Electron 人工点击链已经通过**。本批结束后停下来，第二批仍须另行确认。
