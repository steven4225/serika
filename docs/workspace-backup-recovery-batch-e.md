# E：手动备份，恢复到新位置，打开旧对话与记忆

本批从 A–D 已合并的 main 出发，按 `docs/optimization-route-remaining.md` 交付 E。沿用已有备份、恢复预览与恢复工作区入口；不重做历史存储，不改记忆框架，不新增数据库／向量库或插件系统。

## Before

现有桌面已经能导出 `.serika-backup`、预览范围并创建恢复副本。但大部分存储只检查 JSON 和哈希，哈希正确的坏内容仍可通过预览；可能直到打开恢复工作区才报错。短于八个字符的当前配置凭据出现在正文时，原扫描也不会阻止导出。

## After

用户可以在助手空闲时导出当前工作区的数据，核对范围后恢复到新目录，显式打开恢复后的旧对话与记忆，之后返回原工作区。导出、预览和恢复共用完整清单校验；不能被原 Store 读取的数据，在创建恢复目录前就拒绝。已存在的备份不覆盖，原数据不替换。

恢复沿用既有安全边界：单次旧排期取消、重复排期暂停、执行中的旧任务标记中断、清掉重试和待通知意图；RSS 关闭，不复制配置、服务定义、Telegram 绑定或工具授权。恢复本身不启动模型、任务、通知或服务。显式接回后，仍可在新的恢复工作区正常提问；这不是恢复旧执行权限。

## 范围和校验

- 只包含当前工作区显式登记的 Thread，以及存在的 memory、checkpoint、work-tasks、dreaming、tasks、RSS 数据和归属正确的执行回执。
- 不包含工程文件、`.env`、模型配置、API key／token 凭据文件、Telegram 通道绑定／投递日志、外部 Skill 注册和 launchd 定义。
- 原有同一套 writer flock 保证协作写入停稳后读取；锁有争用就拒绝整次导出，不等到一半才给出“部分成功”。
- 复用各 Store 的既有 schema／兼容校验器和对应读取大小限制，不复制一套简化 schema，不改变原存储的读取、迁移、沉淀或写入规则。
- 清单检查来源、规范时间、Thread 唯一性、路径白名单、文件哈希、消息形状、回执身份／归属／冲突和大小。摘要记录仍由原上下文前缀／摘要机制判断是否可使用，备份不会放宽摘要校验或把摘要当作授权。
- 预览只读；确认恢复时重新核对整个备份 fingerprint。预览后文件被替换，必须重新选择。
- v1 历史与 v3 增量历史都导出成独立可读快照，保留摘要记录；逻辑消息不变。恢复不要求原 delta 链，也不推进记忆游标。
- 多个原目录的回执分别保存；当前追踪列表仍受原 50 Run／256 KiB 上限，超出部分保留在恢复目录 `receipts/` 中，不伪造无限历史面板。
- 正文出现当前宿主已知的配置凭据时拒绝导出，包括短凭据。但程序不能识别所有未知敏感正文；文件没有加密，需放在可信位置。哈希检查一致性，不是备份作者的数字签名。
- 整个备份封装／解压限 128 MiB，超过就拒绝，不截断来源。

## 五分钟 Demo：桌面操作

前提：主助手已经加载本批构建，当前无执行、整理或待确认；至少有一个旧对话和一条正式记忆。恢复副本保存位置应在可信目录。若已启用常驻，打开恢复工作区会要求显式停止主常驻助手；独立后台 worker 不因此自动停止。

1. 点击右上角「设置」（或 `serika` 页签），进入「模块」，找到「数据备份与恢复」，点「导出备份」，选择工作区之外的新文件名。应显示备份路径及对话／文件数量。
2. 点「选择备份恢复…」，选择该文件。核对来源工作区、时间、对话数和数据类型；此时不应产生恢复目录。
3. 点「确认范围并选择保存位置」，创建 `Serika-recovery-*` 新目录。日用数据不被覆盖，旧排期不执行。
4. 没有计时或执行时，点「打开恢复工作区…」并确认。历史里能读旧对话，记忆页能找到旧记忆；没有自动启动历史任务或连接 Telegram。
5. 点「返回原工作区…」并确认，原对话、记忆、配置仍在。项目文件不属于本备份，请另行备份。

失败判据：恢复覆盖原目录；未核对预览就恢复；坏数据被显示为可恢复；打开副本自动执行旧任务；凭据或绑定文件被带入，均不算通过。
