# Serika 最优优化路线 — 给 Codex 的实现任务书

仓库：Serika  
基准：以当前工作树为准；先前审计曾对照 `main@67e9534`／`44cd6c2`。  
原则：**只改日用可靠性，不换架构、不换记忆框架、不上向量库、不做插件内核。**

---

## 总目标

让本机私人助手能「长跑」：长聊还能打开、手机交办不积满、确认卡住能续办、数据可备份；记忆正确性随后补，UI 换皮不换宿主契约。

## 明确不做（本轮）

- 引入 Letta／Hindsight／LangMem／向量数据库
- 整仓迁移 PostgreSQL Durable
- 完整插件依赖图／热卸载／插件市场
- 仅为对齐 Shiori 重做模块操作系统
- 官方 DeepSeek 直连（活链路以 Command Code 为准）
- 通用 Tool Search／Deferred Loading（先测体积）
- 完整 Plan/Execute 产品化（可另开任务，不阻塞本路线）

### 第一批（主线 · 最高优先）：本地数据长期可用

#### 交付项 A — 历史不因文件变大而打不开

**Before：** JSONL 每次追加全量消息快照；桌面历史 16 MiB 拒读；上下文压缩 ≠ 磁盘历史压缩。  
**After：** 长期会话仍能列出、搜索、打开并继续；整理不破坏记忆来源、整理游标、摘要校验，也不误恢复工具授权。

实施要点：

- 减少重复全量快照；建立可恢复的历史整理／增量存储与读取路径。
- 历史列表不再反复解析所有旧快照。
- compact **必须先卡住该 thread 的 append**（含跨进程租约），禁止边 Run 边 compact。
- 保留旧格式读取；不一次性搬迁全部日用数据。
- 验收钉死：整理后记忆游标、摘要校验、工具授权都不被误恢复。

依据：`packages/core/src/jsonl-store.ts`、`apps/desktop/src/main/thread-history.ts`。

**五分钟 Demo：** 准备累计超过原上限、但有效对话较小的历史 → 桌面搜索一句旧话 → 打开原 Thread → 退出重开 → 继续对话；标题／历史／有效摘要可用，旧工具不重放。

#### 交付项 B — 关键回执持久化边界（与 A 同批）

**Before：** `execution-record-store` 为 tmp→writeFile→rename，无 file/dir sync。  
**After：** 与 TelegramStore 同级的持久化边界；写入失败或不确定则停止相关派发，不把未知效果画成失败后自动重试。

依据：`examples/cli/src/execution-record-store.ts`。

**同批处理：** transcript、执行回执、WorkTask、后台任务记录的关键持久化策略一致。

### 第二批：手机交办闭环

#### 交付项 C — Telegram 记录生命周期

**Before：** 入站 ≤1024、投递 ≤2048，无结束记录清理；满后停收，重启不解。  
**After：** 已结束记录可安全归档／清理；待处理、未知效果、未完成投递与去重依据保留；容量问题可见、可处理。不靠清空状态文件。

依据：`apps/desktop/src/main/telegram-store.ts`、`telegram-gateway.ts`。

**Demo：** 从接近上限开始连续收发；重复旧消息不重跑；待核对执行仍能查到。

#### 交付项 D — 过期确认续办

**Before：** 短码五分钟过期后无「当前确认 → 新短码」；重试入口不覆盖确认。  
**After：** 手机可查询当前确认；仍在等待则发绑定同一次操作的新短码，旧码永久失效；一端处理后另一端失效。不复活已结束授权。

依据：`telegram-gateway.ts`（确认校验／短码发布／重试范围）。

**Demo：** 短码过期 → 查当前确认 → 新码批准一次；新旧码都不产生第二次写入。

### 第三批：用户可自助备份

#### 交付项 E — 手动备份／恢复

- 等第一批存储格式稳定后再做（避免刚备份又换布局）。
- 首版手动、无云同步；空闲且相关写入停稳时生成。
- 不打包 API key／机器人 token／环境文件。
- 恢复先校验，不覆盖正在使用的数据；不自动启用服务、重发结果、重新授权。

**Demo：** 生成备份 → 看清范围 → 新位置打开旧对话与记忆；原数据不变，历史任务未自动执行。

### 第五批：记忆正确性（在数据长跑之后，不换框架）

基于 Codex 审计结论，**只修正确性**：

1. **处理覆盖：** 每条来源有结果（已提炼／无需保存／待续）；达提案上限或截断时不得把整批游标前进；防「8 读／5 提案」静默漏记。
2. **固定沉淀工作流：** 宿主准备 → 一次有界结构化提取 → 程序校验 → MemoryStore 原子提交；取消／抢占／超时／不确定提交边界保留。
3. **事实身份（少量常用属性）：** 同属性同场景同义复用来源；值变更走双时态；场景不同可并存；歧义进待确认。
4. **读取投影（可紧随其后）：** 小画像＋相关事实；查询改写按需；后台沉淀合并批处理。

**禁止：** 为腾空间让 LLM 合并删除正式事实；引入新记忆运行时。

## 给 Codex 的开工指令

请从 **第一批交付项 A＋B** 开始实现：

1. 只读摸清 `jsonl-store` 旧格式兼容与 compact 并发边界、`execution-record-store` 写入路径。
2. 实现历史整理／增量读取路径 + 回执 fsync（或等价耐久边界）；写入失败／不确定则停派发。
3. 补测试与五分钟 Demo 步骤说明（写入 PR／提交说明）。
4. **不要**同时开 Telegram、备份、记忆框架替换、UI 重绘。
5. 每完成一批再停下来汇报 Before／After／Demo 结果，等确认后再开下一批。

成功标准（第一批）：超过原 16 MiB 限制的历史能搜索、打开、重开继续；compact 后记忆游标／摘要校验／工具授权不被误恢复；回执写入不确定时不继续派发工具。
