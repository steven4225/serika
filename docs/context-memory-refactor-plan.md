## 1. 数据依据（2026-10-20 本机只读盘点）

- 主对话占全部消息的 83%（1,093 / 1,316），48 条压缩记录。

- 记忆：14 条，其中 7 条确定来自验收、1 条疑似；自然产生的 6 条里，4 条是项目或任务信息、1 条是持续偏好、1 条意思记反了（第 9 条）。244 次沉淀只产出 6 条自然记忆。

## 2. 架构（定稿）

### 2.1 上下文：五层，只往后追加

```
① 系统指令 + 工具（按运行模式固定一套，顺序和字节保持一致）
② 固定参考：用户偏好 + 当前项目笔记（全量）、记忆文档索引、已有方法索引（压缩时才刷新）
③ 摘要：远期索引 ≤2K + 最近几段 ≤4×2K + 不可模糊清单 ≤2K
④ 近期原文（约 48K，只追加；旧工具结果和旧附件在压缩时换成占位）
⑤ 当前消息：时间（到分钟）、任务、检查点、WorkTask 引用、记忆更新附注，随消息一起保存
```

- 开头只在压缩或快照刷新时变化，两件事放在同一时刻做。中途的记忆变化在 ⑤ 附注（如“第 X 条作废”），下次压缩时并入快照。
- **唯一例外**：涉及隐私或用户要求删除的撤回，立即重建受影响的层（见 2.8），这一轮缓存不命中可以接受。
- 各层上限按当前模型的有效输入窗口等比例计算（沿用 #156 的容量绑定），32K 窗口的模型必须能正常运行。
- 屏蔽按块进行，不每轮滑动。
- 自主运行时固定层不带聊天整理类工具（#172 需求）。

### 2.2 摘要

- **远期索引**：每条带时间范围和消息编号范围，例如“10/12–10/15 讨论 TG 多账号（消息 812–905）”。
- **最近几段**：每次压缩追加一段；第 5 段来了，就把最旧一段并入远期索引。
- **不可模糊清单**（永不合并）：
  - 当前目标和约束；
  - 当前交办请求和同一 Run 内的修正（#170 / #171 需求）；
  - 未完成的事；
  - 结果未知的写操作；
  - 权限状态；
  - 最近的真实回执（最多 6 项，沿用 #171 的上限）。
- 不可模糊清单由程序从结构化记录（WorkTask、回执、权限状态、交办请求）直接抽出，不依赖模型生成。
- **行动记录在保存时就精简**：结果未知、失败的全部保留；已完成、未执行的各留最近 8 条，更早的合成一行，注明去原文查。
- 更早的内容不进上下文，提供“搜索历史 / 按编号读消息”工具，直接扫原文。

### 2.3 超限处理（不等模型，不丢原文）

1. 单个工具结果超过约 16K tokens：只放开头和结尾，全文存文件，可按区间读取。
2. 附件或粘贴内容过长：存成附件，上下文只放说明和开头几段；旧附件压缩时换成占位，可按编号重读（#169 的附件功能）。
3. 后台压缩没跟上：直接屏蔽最旧的一块原文，**不等压缩，也不等抽取**，摘要和抽取之后补做。
   - 屏蔽前由程序（不调模型）把这块里的不可模糊信息抽进清单；
   - 屏蔽边界不能拆开工具调用和它的结果；
   - “抽到哪条消息”的进度标记不能越过被屏蔽、但未抽取的块；屏蔽后立即排队，从对话日志补抽（原文在日志里，不丢）。
4. 模型服务仍报超长：按真实用量重算，再屏蔽一块，只重试一次；绝不重放工具。
5. 单条消息本身就超过窗口：截断并放占位，全文可按区间读取。

### 2.4 记忆：长期知识分三类

| 类别 | 内容 | 进入上下文的方式 | 上限 |
|---|---|---|---|
| 用户偏好 | 跨项目的持续偏好，带条件的偏好把条件写进正文 | ② 全量 | 4 KiB |
| 项目笔记 | 当前项目的情况与约定 | ② 全量（只注入当前项目） | 每个项目 4 KiB |
| 记忆文档 | #169 的文件夹、标题、正文；#166 的导入 | ② 只放索引，正文用工具按需读 | 按文档数量设上限 |

- **做事方法（dreaming）暂不纳入**：等上面三类跑稳后再加。已有的方法文档不删，继续按索引按需读，只是不再自动提炼新方法。
- 同一类事物有多个合理值时（如家和公司各一个地址），抽取时存成不同的属性，不算冲突。
- 只在当前对话有用的信息不进记忆，留在该对话的摘要里（替代 #154 / #162 的对话级作用域）。
- 任务决策留在摘要，不进记忆。
- 记忆不授予任何权限（沿用 #162）。
- 群对话（#180，另一条线）不抽取个人记忆；群上下文中每条消息带发言人。
- 多对话（#186）：每个外部对话对应一个独立的 Thread；跨对话只共享用户偏好和项目笔记。同一对话在桌面和 TG 两端追加（#184 需求），每条消息带渠道和接收时间。

偏好和笔记超过上限时，按这个顺序处理：
1. 被取代、被撤回的不占名额；
2. 后台自动合并同类，不弹出来让用户挑；合并本身作为一次“取代”，有回执、可撤销；
3. 还超就降级为按需查（在内存里做关键词检索），不删除。置顶的优先留在全量注入。

### 2.5 写入

- **入口**：
  - 用户明确说“记住 / 别再…… / 这条记错了”：聊天里提供**一个**记忆工具，只有新增、取代、撤回三种操作；
  - 后台沉淀；
  - 记忆页编辑和导入：来源记为手动，不调用模型，精确重复的跳过（沿用 #166）。
- **触发**（满足任一条件）：
  - 未抽取的原文达到阈值：按有效输入窗口比例计算，与近期原文、压缩块用同一个比例基准，且小于一个压缩块（大窗口约 32K；32K 窗口的模型相应缩小）；
  - 对话空闲 30 分钟；
  - 有块被屏蔽但还没抽取：屏蔽后立即补抽（替代原来的“屏蔽前先抽”）。
- **沉淀的输入**：
  - 未抽取的原文，每次最多一个阈值的量：用户和助手的文字保留全文，工具只留名称和结果状态，附件只留说明；
  - 每条消息的编号、时间、渠道、所属对话和项目；
  - 当前全部偏好和笔记（带编号）。
- **调用格式**：原文块放在前、任务指令放在后，和同一块的压缩调用共享缓存。
- **输出**：新增 / 取代 / 撤回，每条带来源消息编号和原话摘录。
- **来源校验**：
  - 来源只能是用户的消息。助手回复、网页、文件、工具结果都不能单独成为来源。保留“事实必须出自用户原话”（`isExactUserQuote`），并排除被排除记录覆盖的消息（见 2.8）。
  - 确认式来源：来源记为**用户表示肯定的那条消息**（编号 + 原话），另附一句助手提议的摘录作为上下文。宿主检查：①两条消息相邻；②助手那条是助手自己回复用户的文字，不是工具结果或网页内容；③用户的回复明确肯定了具体的值。“嗯”“好吧”这类短回复不算。不满足就不记。
  - 助手不能为了凑来源反复问“要我记住吗”。
- **写入即生效**：在原话旁显示回执（沿用 #158 的展示，回执从记忆记录的取代链和来源生成；以后有了操作日志再改为从日志生成）。回执要轻：平时只用一行小字，取代或撤回时才明显提示；撤销一句话就能完成。不设审核队列。
- **生效时间**：等于原话的时间。范围不明确时，按更窄的范围存。
- **同一句话里互相矛盾**：存成一条带“不确定”标注的记忆，回执里提示可以纠正；不再按话题写规则。
- **同一件事同时有两个有效值**（如两条住址都生效）：只在诊断里标出，不弹出来问用户，不自动二选一。
- **每周在 TG 发一次记忆简报**，每条带撤销。

### 2.6 后台

- 每个对话一个后台队列，优先级：压缩 > 补抽和抽取 > 合并。超限屏蔽不调模型，在发请求前同步完成，不进队列。
- 每项都是一次无工具的模型调用，不是 agent；不往对话里写消息，不让对话显示“忙”。用不开思考的快速模型，并设输出上限。
- 后台任务不继承 Shell、浏览器、Herdr、CUA 等工具（沿用 #170 / #175 的边界）。
- 新摘要只在两轮之间换上。

### 2.7 存储与版本

- 先保留 v5 格式，开工前核对字段：必须能记“被哪条取代”“是否置顶”“来源原话（含确认式来源的两段）”，缺了就加字段，迁移一次。
- 候选和审核的写入口彻底停掉，只留一条写入路径。
- 操作日志（只追加）+ 当前表（可以重建）以后再做；用文件锁；记忆文档的元数据（文件夹、标题、顺序）一并保留。
- 进度：每个对话一个“抽到哪条消息”的标记，和写入放在同一次提交；不能越过被屏蔽、但未抽取的块。连续失败 2 次的段落记入“待重抽”清单，空闲时再试一次；记忆页显示“有 N 段没整理”。
- 数据文件带格式版本号；旧版本进程读到更高版本号时只读不写（沿用 #164 / #169 已有的版本拒绝做法）。
- SQLite 暂缓。重新考虑的条件：对话日志超过 100 MiB、日志里出现锁冲突，或需要跨文件事务。

### 2.8 撤回与排除记录

- **普通改值的撤回**：在 ⑤ 附注“第 X 条作废”，下次压缩时并入快照。
- **涉及隐私或用户要求删除的撤回**（“只追加”规则的明确例外）：
  1. 追加一条**排除记录**：排除哪条消息、什么时候、因为什么。原因只记类别（如“隐私”“用户要求删除”），不摘原话。原文那条一个字都不改。
  2. 所有读对话日志的地方都先读排除记录，再跳过对应的消息：组装请求、压缩、抽取、搜索历史、按编号读消息、诊断、导出、eval 离线重放。搜索命中被排除的消息时，只返回“第 X 条已排除”，不给片段。
  3. 立即处理：那条消息还在近期原文里的，换成占位；把覆盖了它的摘要段重新生成一遍；清掉远期索引里对应的条目；撤掉由它抽取出来的记忆，重建记忆快照。这一轮缓存不命中可以接受。
  4. 排除按消息计。撤回时程序列出其他提到同样内容的消息（如后来又提过、助手转述过），在诊断里标出，不自动扩大排除范围。
  5. 聊天界面照常显示被排除的消息，只是不再交给模型。日志原文要不要真删，等用户明确说要删时另行处理。

3. **4b 五层顺序**：记忆快照、文档和方法索引、动态内容移到 ⑤；去掉相关性判断和向量检索。验收：聊天缓存命中率 ≥70%，首个回复的中位等待时间下降。

6. **4d 后台压缩**：分层摘要、远期索引、超限处理、排除记录。验收：用户可见的压缩等待为 0；CF / CE 测试通过；屏蔽不拆开工具调用和结果；被排除的消息在请求、摘要、索引、搜索、按编号读中都取不到。

## 5. 约束

- 只在 `experiment/architecture-v2` 上提交，不改、不合并 main。日常数据只读，迁移只在副本上验证，不重启日用进程。
- 真实模型调用会计费，跑 live eval 或离线重放抽取前先问用户。
- 不为单个失败案例加话题或句式规则；失败了就改提示词或参数，并在报告里写明。
- 不新增 agent、框架、数据库、向量库；不重新引入审核队列。
- 请求开头不放任何每轮会变的内容；不往对话日志写合成消息。
- 不把“结果未知”改写成成功或失败；不重放工具。
- 不靠改测试或改历史分数让结果变绿。
- 回执与 verifier 的不变量 I1–I5 必须原样通过。
- 超出本计划范围的权限、回执、verifier、数据路径、hash、用户可见行为改动，先问用户。
- “少操作”不能被悄悄加回来：不新增弹窗、审核、让用户挑选的步骤；记忆满了在后台合并；冲突只进诊断。
- 每步报告：改了什么（文件和原因）→ 改动前后的指标 → 测试结果 → 与本计划不符的地方及理由。没有实测数字，不能写“已改善”。
