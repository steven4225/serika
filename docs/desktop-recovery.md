# 草稿、补充接收状态与能力切换恢复

## 用户结果

### 一：刷新或重开后，知道刚才写了什么、补充是否接收、窗口是哪版

**Before:** 普通对话草稿与待核对的 Steer 编号仅在页面内存中；刷新会丢失防重复发送状态。版本号不能说明实际加载的代码。

**After:** 普通对话草稿和待核对补充按 workspace、transcript 目录、Thread 隔离保存。页面恢复只读这些信息，不自动发送。模块能力底部「当前版本」显示加载的主进程、页面构建和后端启动产物标识。

**五分钟 Demo:** 在隔离 Electron 中输入一段文字但不发送，看到「草稿已保存」后刷新，再完整退出重开；文字必须原样恢复，不能出现新 Run。打开「模块能力 → 当前版本」，主进程与页面 ID 应一致。窗口开着重新构建后，点「核对磁盘构建」应提示磁盘不同版，但加载 ID 不变；刷新不能伪装成主进程已更新。

丢回包需要受控故障测试：主进程先持久保存请求 id，再调用原 Controller；故意丢失成功响应后，刷新和重启必须恢复待核对提示、保持发送锁定。点「核对接收状态」只查询原 Run 的凭证，不再次调用 Steer。`not_applied` 保留文字，`accepted` / `applied` 只清相同文字，不删新草稿。这不是任务完成或工具授权。

草稿存于 Electron userData 下 `conversation-drafts.json`，文件权限 0600，独占临时文件、fsync、rename、目录 fsync。最多 100 个非空会话、2 MiB，单条普通草稿 64 KiB、补充 4 KiB。超限或坏文件明确报错，不自动丢弃原文件；显示未保存时不要把退出当成保存成功。正常退出等待已进入主进程的写入。

最初这一批只持久化普通对话输入与待核对补充。后续「任务草稿交付」已修正任务正文回到普通对话的行为，见下一节；此前的隔离报告只证明当时版本，不能替代日用验收。

### 后续：任务填写和续做要求不再因刷新而丢失

**Before:** 创建任务的填写内容和按任务区分的续做要求只在页面内存；刷新后丢失，待核对任务补充可能恢复为普通对话正文。

**After:** 同一份 `conversation-drafts.json` 中按可信 workspace、transcript 目录、Thread 保存任务目标、约束、产物路径、人工验收项、测试命令、测试目录、模板选择。续做文字另按 taskId 保存，输入框的任务目标同时恢复。任务暂不可用时明确展示原 taskId，禁用任务发送，不自动转为普通对话。恢复和切换目标只读状态，不开新 Run、不继承确认权限。普通聊天草稿不被任务回执清除。

**五分钟 Demo（日用 Serika，不新建隔离测试窗口）：** 空闲时打开工作任务，创建表单填入上述字段但不提交；看到「任务草稿已保存」后刷新或完整退出重开，再打开工作任务，字段必须相同，执行记录不能新增 Run。已有可续做任务时，选择「补充当前任务」，输入一句要求但不发送；保存后刷新，发送方式仍明确属于同一个任务，正文不进入普通聊天。切回普通对话可看到原普通草稿，两者互不覆盖。

保存失败会显示任务草稿未保存并提供重试，创建/续做及切换 Thread 会等保存完成；坏文件不会当作空表单覆盖。重试包括失败的清空或删除，不会让已清空的旧文字复活。创建成功后只清创建草稿，清理保存失败也不会自动重建任务。`not_applied` 保留原任务文字；接受回执只清同一 taskId 的匹配旧文字，不删除新草稿。每个会话最多 100 份任务续做草稿，每字段 64 KiB，仍受总文件 2 MiB 限额。

当前只覆盖创建任务与续做指令；交付结论、人工验收说明、未知效果核对表单仍不是持久化草稿。单测和服务端静态渲染已覆盖字段恢复、并发字段更新、跨身份隔离、任务 Steer 核对与失败清空；日用五分钟 Demo 需由实际窗口单独核对，不能用这些测试代替。

## 二：切能力失败，不覆盖已发现的配置修改、不把助手假装成可用

**Before:** 模块设置的比较与替换没有合作写入锁；回滚失败会跳过原 Controller 重建。

**After:** 模块、经验开关、显式开启记忆、首次配置与预算补全使用同一配置 flock 事务。失败后尝试重建原会话；仍失败时界面标记连接停止，禁用发送，提供「重新连接」。修正原配置后重连，不调用模型、不创建 Run、不重放工具，不偷偷切到另一 workspace。

**五分钟 Demo:** 在无 Todoist 凭据的隔离配置中打开「模块能力」，开启 Todoist 并保存。应明确显示未应用，模块保持关闭，当前对话和草稿不丢。关闭番茄钟并保存应立即显示关闭。复杂回滚失败与并发写入运行下面的针对性检查；其中竞争写入真实使用两个 Node 子进程，不能仅用内存 mock 证明锁。

```sh
pnpm exec tsx --test src/main/module-settings.test.ts src/main/desktop-config.test.ts src/main/desktop-runtime.test.ts src/main/conversation-draft-store.test.ts src/main/conversation-draft-session.test.ts src/main/build-identity.test.ts
```

锁为 advisory：只能串行合作写入。无视锁的外部编辑器仍可能在最后检查和 rename 之间竞态；没有声称绝对 CAS。发现外部修改时拒绝覆盖；失败回滚也不强制覆盖新配置。
