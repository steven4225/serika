# 第五批：沉淀来源不被上限静默跳过

## Before

沉淀最多准备八条用户来源、生成五条提案，但游标直接到最后一条读取来源。后面三条没提案，或一条消息只处理了部分事实，也可能被跳过。准备、暂存和结束步骤还要由模型选择工具调用。

## After

- 内置 `memory-consolidate`：宿主准备原话和有界冲突材料 → 一个无工具、一模型步骤的 JSON 提取 Run → 程序校验 → 原 MemoryStore 原子提交。这个 Agent 不使用主聊天的模型请求重试；外部注册 Memory Skill 和主聊天的显式准备/暂存工具保持兼容，不新增行为循环。
- 每条准备来源有 `extracted`（该条完整提炼）、`no_memory`（无需保存）、`deferred`（未处理或只处理一部分）结果。提炼结果必须有对应的、原话匹配的提案；无需保存不能同时带提案。程序不能证明模型是否真的提全了语义，不能把该字段宣传为事实正确性保证。
- 游标只推进连续完成的前缀。零推进也可以原子保存合格的部分提案和待续回执；再整理时继续原来源、利用现有记忆/候选去重。旧格式没有 outcomes 时全部待续，不把缺信息当“无需保存”。
- 每个 Thread 只保留最新增量覆盖回执，最多 1024 个 Thread；最多八条 outcome、五个候选 ID、前缀哈希，不复制来源正文。它和候选、自动写入、游标在同一个 v4 `memory.json`、同一 flock/fsync 边界内提交。旧 v1–v4 文件没有该可选字段仍可读取；读取不迁移、不推断旧来源已处理。选定历史只处理选定范围，不覆盖增量待续记录。
- 四种可选属性身份：`response_language`、`review_format`、`coffee`、`residence`；场景限 `general/work/personal`。前三种值使用小枚举，居住地使用有界原词。相同属性/场景/值保留原正文、适用时间，增加已验证来源；不同场景可并存；值不同的 add 转为待审更正，不能自动猜更正或实际变化。明确 change 仍要求 effectiveAt，沿用双时态/CAS。没有身份的旧事实不批量猜测或重写。
- 同一批同义提案可合并来源（仍最多四条），已有待审核项不因新提案而自动接受。当前版本来源上限不变，旧来源留在历史断言；历史/容量满则拒绝，不靠 LLM 删除事实腾空间。

## 五分钟日用 Demo（人工步骤，尚未声称已跑）

前提：已加载本次构建，日用 workspace 的记忆与内置自动沉淀已显式启用，模型连接正常。`automatic` 策略才自动写正式记忆；`review` 策略需用户接受，选定历史始终待审。本批不改这些配置、不重启日用应用。

1. 在当前对话陈述：“我的长期偏好是复盘先结论。我一般喝无糖咖啡。”等整理结束，到「记忆」看来源、正文；如待审先接受。
2. 再说：“我说的复盘格式就是先告诉我结论；咖啡通常不放糖。”等结束，检查同场景的同一属性没有新增第二条正式记忆，保留原正文并能在历史看到新来源。若模型未给可确定身份，应待审，不算此项通过。
3. 说：“更正之前的咖啡偏好，我一般喜欢加糖；这是更正，请记住。”检查同一 ID 增加修订，旧断言仍在。再说“工作时我喜欢无糖咖啡”，检查工作场景可独立存在。
4. 一次陈述“我的六条长期偏好是：计划用周一作周首日、会议不超过半小时、阅读长文先看摘要、工作记录用 Markdown、文件名带日期、提醒提前十分钟”。一次五提案时，在记忆维护区应仍有待整理材料，而不是把该条当完成；再次点击「整理待处理材料」，应能补剩余项，不重复新增已保存事实。审核模式先接受第一批以便第二次看到正式事实。如果模型合成一条完整事实已涵盖六项，不能据此宣称“上限待续”这一项验收通过。
5. 在新 Thread 换种说法询问复盘/咖啡偏好，核对参考记忆的实际 ID/revision。语义召回沿用现有词法/可配置改写，不能只凭模型回答正确就认定本轮注入了它。

通过条件是用户能看到这些完整动作，而不是测试数量。真实模型若漏提案、分类不确定或超时，记录为未通过/待续，不换预算或假装没有信息。
