# 第二批 C＋D：Telegram 用久仍能收发、确认过期能续办

依据：`docs/optimization-route-batch2-plus.md`。仅 C＋D；不重做 A／B，不进入备份、Node 22 门禁或记忆改造。

## Before

活动日志到 1024 条入站／2048 条投递时，不能靠清空状态解决。虽然已有终态归档，归档失败没有冻结接收，恢复旧 Run 时也可能重新发送已归档的结果。确认刷新已有入口，但发送失败仍可能提示“已重新发出”；重启后积压的旧确认消息可能继续投递。

## After

已结束记录先耐久归档，再从活动日志移除；归档只保存关联、去重和核对元数据，不重复保存聊天／结果正文。重启后旧消息不重开 Run，已归档结果不重新发送。待处理、未完成投递及未经核对的未知效果不会为腾空间而删除。

手机发 `/confirm` 或 `当前确认`，可为同一次待确认操作换新短码；旧码立即无效，新码单次使用。权限绑定账号、私聊、Thread、Run、approvalId、toolCallId、工具名及完整输入的哈希，不能用截断预览代替。桌面处理、Steer 替换、到期或重启均不能恢复旧授权。

刷新后的提示区分：平台已接收、明确发送失败、发送结果未知、已保存待发送。平台接收不代表用户已读；未知投递不盲目重发。再次显式 `/confirm` 是创建新的短码请求，而非重放旧消息或重做工具。

## 生命周期与失败边界

- 超过活动容量一半时，归档符合条件的较早终态，保留最近 128 条终态入站／256 条终态投递；硬上限前允许额外释放可归档终态。
- 入站只归档 `finished`、`rejected`、`reviewed`，且 updateId 已在保存的接收位置之前。
- 投递只归档 `submitted`、`cancelled` 或已显式记录核对观察的 `unknown`；未知仍保留原状态，不伪装成功。
- `received`、`reserved`、`bound`、未核对 `unknown` 入站，以及 `pending`、`sending`、`failed`、未核对 `unknown` 投递保留。
- 每个归档文件先 fsync、rename，再同步所在目录；归档层级的目录同步完成后才替换活动日志。归档或写入失败／确认不明冻结该 Store 的后续接收。原活动记录和 offset 不因归档失败而前进。
- 活动日志自身替换后目录同步失败仍属于保存未确认，不声称磁盘没有变化；重启后读取实际记录，不能自动重做任务。
- 旧的可见但未确认归档再次核对内容，并同步目录后才允许释放活动副本。
- 重启把 `sending` 设为 `unknown`，取消尚未发送或明确失败的旧确认消息；发送结果未知的消息保持未知。短码从不从磁盘恢复。
- 发送领取落盘后、调用 Telegram 前再次检查确认是否仍有效；桌面在这段等待期间处理的确认不会继续发送。
- 全是未解决记录时仍拒绝新记录并报告容量问题，不删除它们。先在现有桌面 Telegram 状态入口核对未知效果或停止明确未发出的投递，再重新连接；保存失败冻结的实例需重启后核对。
- 归档去重标记长期保留，活动日志有界不等于总磁盘用量恒定。这不是备份、全文历史库、完整 Durable 或无限容量承诺。

## 五分钟 Demo：可重复的本地验收

入口：仓库根目录，依赖已经安装。命令不读取日用配置、不需要 Telegram token、不发送真实消息；只操作自动创建并清理的临时测试文件。

```sh
pnpm build:runtime
pnpm --filter @aisdk-agent/desktop exec tsx --test --test-name-pattern='full legacy journal resumes|expired confirmation can be renewed' src/main/telegram-gateway.test.ts
```

应看到两个通过的测试，`fail: 0`、`cancelled: 0`，并输出两条 JSON 摘要：

1. `telegram-lifecycle`：旧入站 1024、旧投递 2048；新 Run 共 6 个、旧消息重放 0，未知记录仍保留。包括归档、连续收发、再次打开 Store、旧消息换 updateId 的去重及新消息处理。
2. `telegram-confirmation-renewal`：推进测试时钟使旧码过期；查询新码；旧码不能写文件；新码完成一次真实本地文件写入；重复码不能二次写，Run 不变。

测试使用真实 DesktopRuntime／Controller、文件工具、日志和 fsync，模型与 Telegram 传输是脚本替身。满日志约 2700 个归档文件执行真实同步，测试设 120 秒磁盘时限，不减少记录或放宽断言。该命令不证明真实手机、真实模型或 Electron 点击链。

## 五分钟 Demo：日用手机操作

前提：本批构建已由日用常驻助手加载、Telegram 已绑定本人账号、助手联网空闲。使用一个明确不存在的工作区路径，例如 `notes/telegram-confirm-demo-<唯一后缀>.md`。

1. 手机交办：“请用 write_file 在该路径写入一行 confirm demo，只做这次写入，不保存记忆。”收到当前工具确认后，先不批准。
2. 直接发 `/confirm`，核对新请求的工具和完整可读内容；旧码无效。用新码批准，查看回复和桌面同一个 Run 的成功写入回执。
3. 再发旧码和新码，均应提示无效／已处理；没有第二次写入回执，也没有新 Run。

若要亲眼验证自然过期：先让原确认静置超过五分钟，之后以上续办操作应在五分钟内完成。离线 Demo 用注入时钟覆盖真实过期判断，不修改生产有效期。

真实 Telegram 网络失败／超时、日用 Electron 操作必须另行记录，不能由上述脚本替身冒充通过。本批不自动重启服务、不更改凭据、不向日用机器人发消息。
