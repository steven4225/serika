# Serika Desktop

Electron 前端通过 `createRuntimeApp` + `createAssistantController` 接入后端，不创建第二条 AgentLoop。

## 模型用量分项（Batch 3）

**Before：** 执行追踪只显示已完成聊天步骤的输入／输出／总 Token，无法分辨记忆沉淀、查询改写、摘要压缩和失败重试的用量。

**After：** 「设置 → 执行记录 → 模型用量」按聊天／记忆沉淀／查询改写／上下文压缩（及显式 Skill）分组，每次 SDK 供应商调用尝试单独记录。实际重试分别记账；复用旧摘要或本地改写缓存不新增调用。缓存读／写分别保留，未报告显示「未知」，明确报告的 0 才显示 0。Run 详情只展示关联调用；手动压缩没有 Run，出现在当前对话列表。

账本是现有 `execution-records.json` 的可选元数据，不是第二套执行真相源。启用前历史不回填，独立后台 worker 不在本批观测范围。共享日志最多保留最近 128 次调用；达到字节上限时终态用量先让出空间，不删正在等待的调用，界面显示裁剪数量。进程中断的未完成记录变为结果未知，不重放；取消后的迟到结果不覆盖终态。现有手动备份仅保留执行／工具回执，**不导出这批近期用量元数据**，恢复后不会凭旧总量造账。

费用默认未知。只有外部受信任配置 `modelPricing` 精确匹配界面显示的 `provider` 与 `modelId`，且计费用量完整时才估算；价格按每百万 Token、指定币种，输入单价指非缓存输入。以下仅是配置结构示例，**不是任何供应商真实价格**：

```json
{
  "modelPricing": [{
    "provider": "COPY_EXACT_PROVIDER_FROM_RECORD",
    "modelId": "COPY_EXACT_MODEL_ID_FROM_RECORD",
    "currency": "CNY",
    "inputPerMillion": 2,
    "outputPerMillion": 4,
    "cacheReadPerMillion": 0.2,
    "cacheWritePerMillion": 3
  }]
}
```

供应商未报告缓存写入不等于没写入；缺缓存计数／必要缓存单价、失败／取消／结果未知的请求费用均显示未知。价格随每次调用保存快照，不因后改配置重算历史；**估算≠账单**，不跨币种合计。

**五分钟 Demo（隔离环境，不改日用配置）：** 开启已有记忆自动整理、查询改写及上下文压缩，发一句明确偏好，待主对话与记忆沉淀完成，再从上下文页手动压缩。打开执行记录可展开四组用途并查看缓存与费用。重新读取同一账本不新增记录；再次准备已覆盖的旧摘要／复用同一消息的查询改写缓存，调用数不增加。故障注入验证重试两调用、取消迟到不重账。

离线可复现命令：`pnpm build:runtime && node --test packages/assistant/dist/model-usage.test.js packages/ai-sdk-adapter/dist/token-usage.test.js`。其中 Controller Demo 使用脚本供应商，覆盖真实装配、自动正式记忆写入、四用途账本、摘要复用和重开读取；它不证明真实供应商准确计费或日用 GUI 已加载本批。

## 单仓入口与 Grokbot 检查

当前目录为主仓的 `apps/desktop`。使用根目录 `pnpm-workspace.yaml` / `pnpm-lock.yaml`，不再安装 sibling 仓库。旧前端完整历史保留在导入提交的父链中，旧 checkout 保留作回滚，不再双向开发。下方早期验收记录里的旧绝对路径只是历史证据，不是当前启动入口。

**Before：** Bot 只 clone 后端拿不到 Electron，前端还依赖本机 sibling 路径。

**After：** clone 一个仓库即可安装、审查、构建并测试 Runtime 与桌面。

**Demo：** 在根目录安装后运行 `pnpm build`，有图形桌面的机器运行 `pnpm desktop:dev`；确认是 Electron 窗口、Today 页面能打开任务/记忆/模块，输入和逐次确认仍走原 Controller。日用路径切换后再检查原对话和未发送草稿；不要求手机参与合仓。

### 可交给 Grokbot 的步骤

1. Clone `https://github.com/steven4225/serika.git` 的 `main`，记录实际 commit，读取根目录与本目录 `AGENTS.md`。不要操作用户的 Mac，不获取或输出用户 Key，不改产品代码来让测试通过。
2. 在根目录运行：

   ```sh
   pnpm install --frozen-lockfile
   pnpm typecheck
   pnpm test
   pnpm build
   ```

   若 pnpm 未安装，按根 `packageManager` 安装同版本。Runtime 最低 Node 22.12；当前 pnpm 11 工具链需要 Node ≥22.13（建议用 CI 的 26.4）。CI 单独在 22.12 上直接执行编译后的 Runtime 与桌面测试，不用 pnpm 的版本门槛遮住运行时兼容性。Linux CI 检查 portable 桌面代码，macOS CI 另外构建 Swift 通知 helper。不存在 macOS 环境时，把通知、launchd、系统红绿灯标为 `not_run`。
3. 有可用图形桌面才运行 `pnpm desktop:dev`。`dev` 没配真实模型时明确显示 mock，只用于界面检查，不能写成实际助手能力通过。云机器缺 DISPLAY 或 Electron 系统库时报告具体缺项，不用网页截图冒充 Electron。真实任务需通过 Bot 的安全密钥配置一个外部环境文件，显式设置 `RUNLOOM_MODEL` / `RUNLOOM_ENV_FILE`。
4. 核对：对话输入/草稿、任务/记忆/模块入口、工具确认的允许与拒绝、执行追踪。不要准许测试范围外的 Shell、文件写入或 Computer 操作。分别记录构建、离线测试、真实模型、GUI 和平台专属功能的通过/失败/未运行，不用模型口头结论替代文件与回执。
5. 输出结果，包含 commit、命令退出码、可复现步骤和截图。Telegram 手机确认及退出桌面后的提醒仍是独立日用验收，不是合仓通过条件。

### 日用入口与现有安装迁移（macOS）

```sh
# 根目录；默认读取此处未提交的 .env，或传 RUNLOOM_ENV_FILE 的绝对路径。
pnpm desktop:daily
pnpm desktop:install
```

安装只生成源码 checkout 依赖的本机入口，不是已公证发行包。首次安装不启动应用或后台服务。原 `~/Applications/Serika.app` 若属于旧 checkout，普通安装会拒绝覆盖；确认原应用空闲、没有待确认操作且草稿已保存，完整退出桌面后，显式迁移：

```sh
pnpm desktop:install --migrate-from /absolute/path/to/runloom-desktop
```

只替换与参数中的旧 checkout 匹配的 managed symlink，原 bundle 和旧仓原样保留；命令输出旧 bundle 供回滚。userData 仍为 `~/Library/Application Support/@aisdk-agent/desktop`，bundle ID `app.serika.desktop.local`、`serika://` 和数据格式不变，不搬数据、不导入别的 workspace。

**已有常驻与任务服务：** 先记录旧设置和路径；确认空闲后显式停用。新入口打开后再显式启用同一工作区的常驻服务及任务服务，沿用已有 env 文件和任务，不重复创建提醒。宿主入口和内置通知 helper 路径会变化；不把“已注册”当作新配置已生效，不自动替换不兼容服务。若暂不切服务，仍可审查/测试本 PR，但日用迁移不能写成已完成。

**回滚：** 完整退出新桌面、显式停用新路径服务；在主仓根目录调用同一个受测安装函数，使用迁移命令输出的旧 bundle：

```sh
node --input-type=module -e '
import { installLocalLauncher } from "./apps/desktop/scripts/install-local.mjs";
await installLocalLauncher({
  desktop: "/absolute/path/to/runloom-desktop",
  bundle: "/absolute/path/to/runloom-desktop/dist/local-44.4.5/Serika.app",
  migrateFrom: "/absolute/path/to/aisdk-agent-framework/apps/desktop"
});'
```

替换示例绝对路径和旧 Electron 版本为输出值，不猜目标。该操作同样校验两边 marker；恢复旧服务参数后重新打开。只恢复入口和服务，不回滚用户数据，不覆盖未经校验的安装。

## Telegram 私聊入口与提醒投递

Before：只能在桌面交办，手机不能处理同一次工具确认。

After：显式启用常驻助手后，可绑定一个 Telegram 账号，在私聊提问、用文字交办 WorkTask、逐次批准工具、Steer 和停止。桌面打开 Telegram 对话看到同一个 Thread、Run 和回执。应用仍是 Electron，不是网页机器人；Telegram 网关不会创建第二套 AgentLoop。

配置与使用：

常驻 Node 服务不会自动读取 macOS 的系统代理。若本机使用代理访问 Telegram，在同一可信环境文件显式添加 `TELEGRAM_PROXY_URL=http://127.0.0.1:实际端口`，空闲时重启服务。它只影响 Telegram，不更改模型或其他模块的全局网络设置；代理不可用不会静默回退直连，发送超时仍保留为 `unknown`、不自动重发。

1. 在**常驻服务实际使用的外部环境文件**中添加 `TELEGRAM_BOT_TOKEN=...`，Token 从 Telegram 官方 `@BotFather` 获取。日用默认沿用后端 `.env`，若指定了 `RUNLOOM_HOST_ENV_FILE` 则使用该文件。不要把 Token 发到聊天里、写入 workspace、Git、plist 或 renderer。修改后需在空闲且番茄钟结束时停止并重新启用常驻服务。
2. 打开「serika → 模块能力」，先确认常驻助手已连接，再预览并连接 Telegram。默认关闭，不在应用启动时偷偷注册或绑定。使用 Bot API `getUpdates` 长轮询；已有 webhook 时明确失败，不删除它。不支持群聊、附件、转发消息和机器人代发。
3. 点击「生成一次性绑定码」，在机器人私聊发送 `/start 绑定码`。刷新桌面，核对账号和私聊 ID，再点「确认这是我的账号并绑定」。私聊消息本身不能取得控制权。绑定在五分钟后过期；原绑定不会被新账号覆盖。
4. 直接发文本是普通对话；`任务：目标` / `/task 目标` 生成预览，发送 `开始 短码` 后才创建并运行现有 WorkTask。第一版不从随意聊天猜任务、不让模型编造自动验收条件，使用用户质量项，交付与质量验收回桌面完成。任务目标确认不是工具授权。
5. 工具确认严格使用 `允许 短码` / `拒绝 短码`；只绑定这一账号、私聊、Run、approvalId 和实际工具输入，五分钟有效、单次消费。过期或丢失时发送 `/confirm`（或 `当前确认`），仅在原执行仍等待同一次确认时发新码，同时撤销旧码；不创建 Run、不延长执行预算。普通“可以”不授权。桌面先处理后，旧短码失效；Steer 也不恢复旧授权。`调整：新方向` 走原来的安全边界；`停止` 只停止这条 Telegram 执行，不取消其他对话。

五分钟 Demo（需真实机器人 Token、本人绑定、Mac 保持运行联网）：私聊要求创建工作区根目录 `im-demo.md`；确认前文件不存在；复制当前短码允许这一次写入；重复短码必须被拒绝；桌面打开 Telegram 对话，核对相同 Run 的成功工具回执与实际文件。写入结果不等于后续读回验证；如请求读回，仍需确认那一次读取。

恢复与隐私边界：入站文本与轮询 offset 同笔保存，来源/Run 关联在模型启动前落盘。绑定与收发记录放在当前工作区对应的 resident 私有状态目录 `telegram.json`，不作为执行真相或正式记忆。只有已绑定账号的普通文本进入原有对话沉淀；确认、控制指令与提醒回显不作为用户事实。忙时明确拒绝、不排队。重启后的旧授权失效；已开始但未知的消息不重放，回桌面核对。观察报告只解除通道待核对，不改旧回执、不证明成功；WorkTask 的 `needs_review` 必须先走原任务核对。

发送先保存意图，再调用 `sendMessage`；`submitted` 只说明 Telegram 返回消息 ID，不证明你已收到或阅读。明确拒绝是 `failed`，超时/丢失回应是 `unknown`，不会盲目重发。确定已保存的终态回执可恢复待投递结果，不再调用模型；恢复预览截断会明确标注。活动记录仍有界：超过整理阈值时先持久化已结束记录到私有 `telegram-archive`，再缩减活动日志；新归档只保留去重/归属元数据，不含消息正文，旧归档不自动改写。未知效果、未处理入站和失败投递不擅自裁剪。Telegram 面板显示入站/投递容量；明确未发送的消息可停止投递，未知投递须填写真实观察报告后才可归档，原状态仍是 unknown，不改执行回执或重做任务。若未解决记录本身占满容量，仍明确停止，不静默丢弃。归档元数据随使用增长，不声称磁盘无限容量。重复更新、强制退出和离线网络测试仍不能代替上述日用 Demo。

### 关掉桌面之后接收提醒

Before：任务结果只能在桌面或系统通知查看，执行成功与 Telegram 发送成功无法分开核对。

After：在已绑定私聊里创建完整提醒/简报安排，批准时明确显示该私聊作为目的地。宿主将已保存的任务 ID 登记到通道记录，再启用原有受限 worker；不是第二套调度器或 AgentLoop。旧桌面安排只有在「serika → 模块能力 → Telegram → 提醒与简报投递」预览、确认后才外发。一次性安排必须未结束；定期安排只发送选择之后的新发生项，不倒灌历史。

五分钟 Demo：在私聊要求两分钟后提醒，批准 `task_create`，核对已排期和后台服务状态；空闲且草稿保存后退出 Electron，到点在 Telegram 收到正文；重开桌面查看同一任务和平台消息 ID。Mac 必须保持运行、联网，常驻助手和任务 worker 都须启用。模型解释的“已安排”不替代成功创建回执。

宿主在原来的长轮询循环中读取已选安排的确定终态；正常情况下最多增加约 30 秒投递延迟。保存正文和目的地后才发送，重启可从归属正确的 TaskStore 终态补建待发送项，不再调用模型或执行任务。每轮分页扫描最多 1000 个定期发生项，逐页保存游标、投递已找到结果；超过时下轮续查，不再因旧历史过长整轮失败。遍历结束后重新检查近期记录，允许发现后来才结束的发生项；选择前的历史不外发。RSS 成功但无通知意图表示没有新条目，不发送空简报。中断任务可投递中断说明，但不会重跑。

## 长对话与手动数据备份

Before：长期对话的重复全量快照可能累积超过历史读取限额；大于 8 MiB 的一次历史 RPC 会断开常驻连接；没有桌面备份入口。

After：历史列表流式读取完整记录，对话先显示有界最近页，点击「查看更早的对话」逐页加载。新写入采用 v3 增量记录，只保存变化的消息后缀；正文按 192 KiB 分块，最后一条提交记录校验前缀和载荷哈希。旧 v1 全量记录仍可读，单行上限改为 128 MiB；新的一次增量载荷也有 128 MiB 上限。未完整提交的一组分块不展示为已保存。正常写入在跨进程同一锁内整理冗余快照为检查点，不删消息、不把模型摘要当磁盘压缩。大型 RPC 响应分块传输，单个响应最多 32 MiB；极端大的一条消息仍可能超过 RPC 上限，并非无限历史承诺。重连不重发操作。

「serika → 模块能力 → 数据备份与恢复」可以选择导出位置。备份包含当前工作区已登记对话（含上下文摘要）、正式记忆、checkpoint、任务、RSS、经验和执行回执；不包含项目文件、环境/配置文件、Telegram 绑定凭据或 launchd 定义。已知当前凭据值若出现在正文中会拒绝导出，但无法替你识别所有敏感内容。导出先取得所有相关现有写锁再读取；有存储正在写入就拒绝，不输出部分备份。它保证协作写入不穿插到读取期间，不是全项目数据库事务，也不防绕过锁的外部编辑器。

恢复先只读预览来源和范围，再创建新目录和 `recovery.json`，核对预览后文件发生变化会拒绝恢复。单次未执行任务取消、重复安排暂停、遗留执行中断，不恢复未来通知意图或授权；创建副本不会启动服务、模型或工具。原始回执另存 `receipts/`，当前可用回执仍遵守原保留上限。随后可显式「打开恢复工作区」，停止当前主常驻助手并接回旧 Thread 和记忆；恢复区使用独立安全配置，Shell 和自动记忆整理默认关闭，不复制授权、Telegram 绑定或服务。独立后台 worker 不随界面切换停止。原工作区保持不变，重启仍打开恢复区，面板可显式返回原工作区。忙碌、有番茄钟或显式身份覆盖的入口拒绝切换；保存入口不确定则暂停新执行，必须退出重开核对，不能猜测回滚。

第一批五分钟 Demo：在正常日用入口打开一条长对话，点击更早的对话，核对顺序和连接未断；在 Telegram 面板查看容量，对明确失败的消息选择停止投递，或为未知项记录实际观察，原 Run 数不增加。手机确认续办单独验证：让确认超过五分钟后发送 `/confirm`，只批准新短码，桌面同一 Run 应只有一次工具调用（包含等待时间，不声称五分钟内验证过期）。

第二批五分钟 Demo（助手空闲、草稿已保存、没有番茄钟）：在模块能力导出备份，再选择它，核对范围并创建副本；点击「打开恢复工作区」并确认，看到旧对话和正式记忆。继续发送一条不调用工具、不保存记忆的消息，退出重开后应仍在恢复区且新消息还在；最后返回原工作区，原历史未被副本覆盖。此 Demo 有模型费用；不启用恢复区后台服务。项目文件仍须另行备份。

数据版本说明：旧版本读取器会跳过 v3，不能用于查看本版本新增的对话内容。回退程序前先导出备份（归档含可独立读取的全量 transcript）；不要直接以旧版覆盖新数据。

### 执行中补充要求（Steer）

前台用户任务运行中（包括等待工具确认），输入框可发送「补充要求」。它进入同一个 Run，不启动新任务；正在执行的工具不会被撤销，未派发的旧操作会停止，旧确认会失效，新调用仍需重新确认。工作任务的目标和验收条件不会因此被修改。整理、手动 Skill 和后台任务不接受 Steer。

界面按实际凭证显示「已接收，等待当前步骤结束」「已加入后续规划」或「本轮未应用」。加入规划不证明模型已遵从，也不证明工具已执行。本条默认不整理为长期记忆。运行已结束、预算不足等未应用内容可显式移回草稿，不自动重发。

## 工作任务（桌面第一批）

对话输入区有「创建工作任务」；已有文字时为「作为任务…」，复制目标但保留普通聊天草稿。侧栏「工作任务」可查本对话的任务。普通消息仍只走 `run()`，不自动建任务；定时提醒的 scheduler / worker 是另一套入口，本批没有修改。

1. 先填目标、相对工作区的产物路径和人工验收项，直接看到「这项任务如何算完成」。模板、约束和测试命令按需展开。至少一项验收，表单生成的项目全部为必需项；「创建任务，不执行」只保存任务，不调用模型。
2. 创建后回到对话。任务卡上的「准备开始任务」或「补充要求并继续」只选中输入方式；主屏同一个输入框明确区分「普通对话 / 补充当前任务」。点「开始任务 / 继续此任务」才调用 `runWorkTask()`，空补充指令使用任务目标。每次工具调用仍用当前 `approvalId` 确认。各任务的补充草稿分别保留，启动失败、版本冲突或响应丢失不清空、不重发；任务尚未读到或已切换时锁住任务发送，不偷偷改成聊天。草稿只在当前页面进程内保留，不承诺退出后恢复。
3. 主屏任务卡按实际状态给出下一步：待开始、正在执行、本轮结束未验收、效果待核对、交付待验收、验收通过。支持的自动检查通过后，后端可以提交交付；含人工项的任务停在等待审核，未通过则保持暂停或待核对。在同一窗口点「查看产物并审核」，读取当前文件，再逐项预览并确认人工决定。未自动交付时仍可显式提交结论、产物引用和未解决事项。自动验收只核对最新归属正确的 primary Run 回执与当前磁盘；文件预先存在、助手声称成功、人类核对记录都不算程序通过。所有必需项通过后才显示「验收通过」；重新交付会重置验收。
4. 重启用原配置、workspace、Thread、transcript 后重新读取存储。`needs_review` 先读最新回执，核对实际文件/应用，再填写观察与说明。「仍然不确定」不能继续，但可带核对记录取消；不存在直接取消绕过。成功继续只回到 `paused`，必须另点下一轮，不重放工具。回执缺失或不可用会明示，人类报告仍不是程序证据。

主屏保留任务卡与对话，运行时任务卡缩小，让位于确认卡和执行进度。产物和验收在同窗口详情中展开，ID、约束、关联 Run、续做与压缩信息默认收起；返回详情恢复阅读位置，没有新任务队列或权限。执行记录可回到归属任务。核对后的旧 `unknown` 回执原样保留，只从尚待处理的横幅数量中去除；核对不代表旧执行成功。

### 五分钟亲眼验证

前提：日用入口已配置真实模型，`read-file` 模块已启用；在一个不含敏感材料的工作区准备根目录 `work-plan.md`，含「项目背景」原文与「下一步：待补充」。

1. 在对话输入「读取 work-plan.md，保留项目背景，只把下一步改为两条可执行行动；先读、编辑后读回」，点「作为任务…」。填产物 `work-plan.md`、人工项「背景保留、恰好两条行动」，核对验收摘要后创建。
2. 确认回到主屏为「待开始」，没有执行。点「准备开始任务」，在同一个输入框可补充两条具体行动，再点「开始任务」。逐次查看并允许该文件的读取、编辑、读回；不批准无关路径或 Shell。
3. 程序检查通过后应显示「等待你审核」，不能先变成全部通过。点「查看产物并审核」→「查看产物」，核对磁盘正文。点「通过此项」→「确认验收决定」，任务才显示「验收通过」。回到对话仍能继续普通聊天。

## 正式记忆与引用说明

记忆抽屉分成“正式记忆 / 候选记录”，不是把接受候选时的回执当作当前正文。正式记忆列表有有界预览；详情展示完整正文、保存来源原话、scope、revision、有效期和固定状态。只能看工作区和当前 Thread 的记忆。
